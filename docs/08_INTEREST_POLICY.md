# 08. Interest Policy

| 항목 | 내용 |
|---|---|
| 문서 상태 | Draft v0.1 (Step 5) |
| 작성일 | 2026-09-07 |
| 선행 문서 | 02_PRD (FR-1, FR-16), 06_SCREEN_REQUIREMENTS (3.1.4) |

Interest는 이 서비스의 유일한 매칭 재료다. 관심사 목록의 품질과 사용자의 선택 품질이 곧 추천 품질이다(Risk: Interest Quality). 이 문서는 관심사를 누가 만들고, 사용자가 어떻게 고르고, 어떻게 바뀌는지를 정한다.

---

## 1. 제공 주체와 구조

| 결정 | 내용 | 이유 |
|---|---|---|
| 제공 주체 | **운영자**가 목록을 준비한다. 사용자는 목록에서 고르기만 한다 | 자유 입력은 "백엔드/백앤드/Backend"처럼 같은 뜻이 흩어져 공통 관심사 계산을 망친다 |
| 초기 규모 | **약 100개**, Category 8~10개 | 1,000명 × 평균 7개 = 7,000회 선택. 100개면 관심사당 평균 70명. 겹침이 생길 만큼 적고, 취향을 표현할 만큼 많다 |
| 구조 | Category(대분류) > Interest 2단계. 3단계는 두지 않는다 | 온보딩 화면이 한 목록으로 훑을 수 있어야 한다(06 §3.1.4) |
| 이름 규칙 | 한글 기본, 널리 쓰이는 영문 약어(AI, OSS, DevOps)는 그대로. 한 관심사에 하나의 이름 | 검색과 표시의 일관성 |

### 초기 Category 초안 (운영자가 확정)

| Category | 예시 Interest | 비고 |
|---|---|---|
| 개발 | 백엔드, 프론트엔드, 모바일, AI, 데이터, DevOps, OSS, 알고리즘, 보안, 게임 개발 | 개발자 조직이면 가장 붐빔. Popular Interest Bias의 진원지 |
| 커리어 | 취업 준비, 이직, 창업, 면접, 포트폴리오 | "이야기하고 싶은 주제"로서 강함 |
| 학습 | 영어 회화, 자격증, 독서, 글쓰기, 스터디 | |
| 스포츠 | 축구, 농구, 야구, 러닝, 클라이밍, 헬스, 배드민턴, 수영, 골프, 테니스 | |
| 문화 | 영화, 음악, 공연, 전시, 애니메이션, 웹툰 | |
| 게임 | PC 게임, 콘솔 게임, 보드게임 | "게임 개발"과 구분 |
| 라이프 | 여행, 카페, 맛집, 요리, 반려동물, 사진, 캠핑 | |
| 기타 | 봉사, 투자, 자동차, 패션 | |

- 같은 Category 안에서 사람 수가 극단적으로 쏠리면(예: "개발" Category의 절반이 "백엔드") Category를 쪼개는 것을 검토한다.
- "이야기할 거리"가 되지 않는 관심사(예: "잠")는 넣지 않는다. 기준은 "이 관심사로 처음 만난 사람과 10분 대화가 가능한가".

## 2. 사용자 선택 규칙

| 파라미터 | 값 | 왜 이 값인가 | 너무 높으면 | 너무 낮으면 | 조정 데이터 |
|---|---|---|---|---|---|
| P-01 최소 | **5** | 5개면 다른 사람과 3개가 겹칠 확률이 생긴다. 3개 이하면 Similar People 기준(P-03=3)을 만족하는 사람이 거의 없다 | 온보딩 이탈. "고를 게 없다" | 그래프가 희소. 추천 0명이 대다수 | 온보딩 완료율, 완료자의 선택 개수 분포, 추천 0명 비율 |
| P-02 최대 | **15** | 100개 중 15개면 15%. 이 이상은 "관심사"가 아니라 "관심 없지 않은 것"이 된다 | Interest Inflation. 공통 관심사 개수가 부풀어 추천 의미 상실 | 표현 부족. 취미와 개발을 모두 담기 어려움 | 15개 꽉 채운 사용자 비율, 그들의 요청 수락률(낮으면 인플레이션 신호) |

- 선택 개수와 함께 **Category 분산은 강제하지 않는다.** "개발만 10개"도 허용한다. 다만 온보딩에서 "취미도 하나 넣으면 다른 이야기를 할 사람을 만날 수 있습니다"를 한 번 권한다.
- 각 관심사 옆에 가진 사람 수를 보여준다. 이는 유도이지 강제가 아니다.

## 3. 변경

| 결정 | 내용 |
|---|---|
| 변경 가능 여부 | **언제든 가능.** 저장 즉시 그래프와 추천에 반영 |
| 변경 빈도 제한 | MVP에서는 없음. 대신 변경 이력을 기록해 Interest Inflation(추천을 늘리려 자주 바꾸는 행동)을 관찰한다 |
| 진행 중 요청에 미치는 영향 | 요청 당시의 공통 관심사는 요청에 남는다. 상대가 요청 화면에서 보는 공통 관심사는 "요청 당시" 기준. 변경으로 요청이 무효가 되지는 않는다 |
| 연결된 사람에게 미치는 영향 | 연결은 유지된다. 연결 화면의 공통 관심사는 현재 기준으로 갱신 |
| 관심사를 최소 미만으로 줄이기 | 불가. 저장 버튼 비활성 |

## 4. 제안 (S4)

| 결정 | 내용 |
|---|---|
| 누가 | 모든 사용자 |
| 어떻게 | 이름 입력. 입력 중 비슷한 기존 관심사를 보여줘 중복 제안을 줄인다 |
| 처리 | 운영자가 확인. 채택 / 기존 관심사로 안내 / 반려 |
| 채택 시 | 목록에 추가. 제안자에게 알림 + "내 관심사에 추가할까요?" |
| 반려 시 | 제안자에게 사유 한 줄 |
| 기준 | 같은 뜻의 기존 관심사가 없고, "10분 대화" 기준을 만족하며, 제안이 2건 이상 들어왔거나 운영자가 타당하다고 판단 |
| 시점 | 사용이 2주에 집중되므로 첫 주에는 **매일** 제안을 확인한다. 채택이 늦으면 제안자가 떠난 뒤다 |

## 5. 운영자 관리

| 작업 | 규칙 | 사용자에게 |
|---|---|---|
| 추가 | 언제든. Category 지정 필수 | 안내 없음. 묶음 알림에 "새 관심사 N개" 포함 가능 |
| 이름 변경 | 뜻이 같을 때만(오타, 표기 통일) | 안내 없음. 선택은 유지 |
| 병합 (중복 처리) | A를 B로 합침. A를 가진 사람은 B를 갖게 됨. 둘 다 가졌던 사람은 하나만 | 영향받은 사용자에게 "○○가 △△로 합쳐졌습니다" 알림. 최대 개수 초과가 생기면 초과를 허용하고 다음 수정 때 정리하도록 |
| 숨김 (삭제 대신) | 목록에서 사라지고 새로 고를 수 없음. 이미 가진 사람에게는 유지되되 "숨겨진 관심사" 표시 | 영향받은 사용자에게 알림 + 대체 관심사 제안 |
| 삭제 | MVP에서는 하지 않는다. 숨김으로 대신 | — |
| Category 이동 | 언제든 | 안내 없음 |

운영자 UI는 MVP에 없다(L6). 위 작업은 운영자가 직접 데이터를 다루는 것으로 충분하다. 단, 병합과 숨김은 사용자 알림을 동반하므로 신중히 한다.

## 6. 인기 관심사와 희소 관심사

| 상황 | 정의 (가설) | 문제 | 대응 |
|---|---|---|---|
| 너무 인기 많은 관심사 | 전체의 **30% 이상**이 가진 관심사 | 공통 관심사 개수를 부풀린다. "백엔드+알고리즘+취업준비" 3개가 겹치는 사람이 수백 명 | 목록에서 제거하지 않는다. 대신 (1) 추천 정렬에서 희소성 가중(13_RECOMMENDATION_PRINCIPLES), (2) 그래프 사람 표시 상한, (3) 운영자가 세분화 검토(예: 백엔드 → 백엔드/Spring, 백엔드/Node) |
| 거의 사용되지 않는 관심사 | 공개 2주 후 **3명 미만** | 그래프에 외딴 점. 고른 사람은 "아무도 없네" | MVP 기간 중 유지. 그 관심사 상세에 빈 상태 안내(06 §4). MVP 후 숨김 검토 |
| 희소하지만 강한 관심사 | 3~15명이 가진 관심사 | 문제가 아니라 기회. 이 사람들끼리는 공통 1개로도 이야기가 된다 | 추천 정렬에서 우대. 장기적으로 "희소 관심사 1개 공통"만으로 추천하는 규칙 검토(Later) |

---

## 7. 관심사와 개인정보

- 관심사는 **조직 내 모든 구성원에게 공개**된다. 비공개 관심사는 없다. 비공개면 매칭 재료가 되지 않으므로 존재 이유가 없다.
- 온보딩에서 "선택한 관심사는 다른 구성원에게 보입니다"를 명시한다. 민감할 수 있는 관심사(종교, 정치, 건강)는 목록에 넣지 않는다.

## 결정 / 미결정

### 결정됨

- 운영자 제공, 약 100개, 2단계 구조. 사용자 자유 생성 없음.
- 최소 5, 최대 15. Category 분산 강제 없음.
- 변경은 언제든, 즉시 반영. 빈도 제한 없이 이력만 관찰.
- 제안은 운영자 검토, 첫 주 매일 확인. 채택 시 제안자에게 추가 제안.
- 삭제 대신 숨김. 병합과 숨김은 사용자 알림 동반.
- 인기 관심사는 제거하지 않고 추천 가중으로 대응.
- 관심사는 전원 공개. 민감 주제는 목록에서 배제.
