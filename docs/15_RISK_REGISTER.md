## 1. 제품 리스크

### R-01 Graph Novelty

| 항목 | 내용 |
|---|---|
| 설명 | 처음에는 재미있지만 재방문 이유가 없다. 그래프를 한 번 보고 끝난다 |
| Likelihood | **High** |
| Impact | High. H9 실패 = 2주 후 아무도 없음 |
| 완화 | 재방문 동력을 그래프가 아닌 "나에게 온 것"(요청, 수락, 성립, 추천)으로 설계(02 §2.3). 외부 채널 즉시 알림 Must(M11). 집중 2주 동안 묶음 알림 일 1회(P-12). 온보딩 즉시 Network 1개 노출(10 §2a) |
| MVP 대응 | **필요.** 이미 반영 |
| 관찰 지표 | 2주차 재방문율, 알림 경유 재방문 비율 |

### R-02 Hairball

| 항목 | 내용 |
|---|---|
| 설명 | 그래프가 복잡해 읽을 수 없다. Phase 0의 25명에서도 Network 모드 선이 과다했다 |
| Likelihood | **High** (대응 없으면 확실) |
| Impact | High. 그래프가 서비스의 정체성 |
| 완화 | 사용자 중심 부분 그래프(사람 30, 인접 관심사 8), 앵커 개념, Network 허브 노드, Similar 선 상위 10명(06 §1). 세부 값은 앱을 만든 뒤 조정 |
| MVP 대응 | **필요.** 이미 반영. 첫 구현 후 실사용 피드백으로 상한 조정 |
| 관찰 지표 | 그래프에서 사람 클릭 전환율, "N명 더 보기" 사용률, 앵커 변경 사용률 |

### R-03 Interest Quality

| 항목 | 내용 |
|---|---|
| 설명 | 관심사 목록이 나쁘거나 사용자가 대충 고르면 추천이 무의미하다 |
| Likelihood | Medium |
| Impact | **High.** H1 실패 = 모든 것의 실패 |
| 완화 | 운영자 제공 100개, "10분 대화" 기준(08 §1), 최소 5개, 각 관심사에 사람 수 표시, 제안 첫 주 매일 처리, 병합/숨김으로 목록 정리 |
| MVP 대응 | **필요.** 초기 목록 품질은 운영자(사용자)의 준비에 달려 있다 |
| 관찰 지표 | 평균 관심사 수, 최소만 고른 비율, 제안 건수, 관심사별 분포 |

### R-04 Popular Interest Bias

| 항목 | 내용 |
|---|---|
| 설명 | "백엔드+알고리즘+취업준비"처럼 절반이 가진 관심사가 공통 개수를 부풀려 추천을 지배한다. 개발자 조직에서 특히 심하다 |
| Likelihood | **High** |
| Impact | Medium. 추천은 나오지만 "누구나 비슷"해져 의미가 없다 |
| 완화 | 정렬에 희소성 가중(13 §3.2), 인기 관심사 세분화 검토(08 §6), Network 교집합 5개 기준(인기 3개만으로는 안 묶임), P-04를 3까지는 낮추지 않음 |
| MVP 대응 | **필요.** 희소성 가중은 Must 정렬 규칙에 포함 |
| 관찰 지표 | 관심사별 보유 비율(30% 초과 개수), 추천 상위의 공통 관심사 구성 |

### R-05 Interest Inflation

| 항목 | 내용 |
|---|---|
| 설명 | 추천을 많이 받으려고 관심사를 최대로 채우거나 자주 바꾼다 |
| Likelihood | Medium |
| Impact | Medium. 공통 개수의 신호 가치 하락 |
| 완화 | 최대 15개, 변경 이력 관찰, 15개 채운 사용자의 수락률 비교(14 §3) |
| MVP 대응 | 관찰만. 빈도 제한은 데이터 후 |
| 관찰 지표 | 15개 비율, 변경 빈도, 15개 사용자의 수락률 |

### R-06 Connection Spam

| 항목 | 내용 |
|---|---|
| 설명 | 무작위·대량 요청. 특히 **차단 기능이 없으므로** 받는 쪽이 스스로 막을 수단이 거절뿐이다 |
| Likelihood | Medium (조직 내부 실명 기반이라 낮아짐) |
| Impact | High. 받는 쪽의 이탈 |
| 완화 | 메시지 필수, 일 5 / 주 20, 취소 시 복구 없음, 동일 메시지 3회 안내, 수락률 10% 미만 감속, 거절 후 14일 재요청 불가, 신고 2회 누적 시 운영자 정지(09 §3, §9) |
| MVP 대응 | **필요.** 차단 부재를 보완하는 장치이므로 전부 Must에 포함 |
| 관찰 지표 | 상한 도달 비율, 동일 메시지 비율, 신고 건수, 감속 적용 사용자 수 |

### R-07 Rejection Fatigue

| 항목 | 내용 |
|---|---|
| 설명 | 요청과 추천이 너무 많이 도착해 처리 자체가 부담이 된다 |
| Likelihood | Medium (집중 2주 동안 High 가능) |
| Impact | Medium |
| 완화 | 요청 만료 3일, 거절 비통보와 5초 되돌리기, Network 슬롯 3개, 알림에 판단 근거 포함, 채널별 on/off |
| MVP 대응 | 필요. 이미 반영 |
| 관찰 지표 | 1인당 받은 요청 수 분포, 만료율, 알림 끔 비율 |

### R-08 Recommendation Fatigue

| 항목 | 내용 |
|---|---|
| 설명 | 같은 사람이 계속 추천된다. 처리한 사람이 목록에 남아 지루하다 |
| Likelihood | Medium |
| Impact | Low (2주 기간에는 제한적) |
| 완화 | 처리한 사람은 상태 표시 + "새 사람만 보기" 필터(13 §3.4), 신규 가입자 정렬 3차 기준, Network 중복 추천 방지 |
| MVP 대응 | 최소만. 추천 숨기기는 Later(L9) |
| 관찰 지표 | Similar 재방문 시 새 사람 비율 |

### R-09 Network Awkwardness

| 항목 | 내용 |
|---|---|
| 설명 | 그룹이 성립됐지만 아무도 메신저에서 시작하지 않는다 |
| Likelihood | **High** |
| Impact | Medium (Should 기능). 그러나 H6 판단을 망친다 |
| 완화 | 시작자 지정(첫 참여자), 역할을 "그룹 열고 초대"로 한정, 실명 목록 복사, 1일 후 재안내, 후속 확인(10 §5~6) |
| MVP 대응 | 필요. Action 안내는 Must |
| 관찰 지표 | "초대했어요" 표시율, Network 후속 확인 "대화 시작" 비율 |

### R-10 Community Scope Creep

| 항목 | 내용 |
|---|---|
| 설명 | 게시글이 커뮤니티가 되어 서비스 목적이 흐려진다 |
| Likelihood | Low (2주 기간, 기능 빈약) |
| Impact | Medium |
| 완화 | 댓글·좋아요·피드·검색 없음, 관심사당 하루 1개, 300자, 글의 출구는 연결 요청뿐, 감시 신호 5개(11 §5, §7) |
| MVP 대응 | 이미 반영. S1 자체가 Should |
| 관찰 지표 | 글 → 프로필 이동률, 글 길이 분포, 작성 빈도 |

## 2. 추가로 식별한 리스크

### R-11 Cold Start (초기 사용자 부족)

| 항목 | 내용 |
|---|---|
| 설명 | 공개 첫날 가입자가 적으면 그래프가 비고 추천이 0명이다. 첫 인상이 "아무도 없네"가 되면 재방문하지 않는다 |
| Likelihood | **High** (첫 수 시간) |
| Impact | High |
| 완화 | 빈 상태 안내 + "생기면 알려드립니다"(06 §4), 운영자와 지인이 먼저 가입해 시드 확보, 초대 링크를 한 번에 넓게 공유, 온보딩 즉시 Network 노출로 초기 밀도 활용 |
| MVP 대응 | **필요.** 운영 계획: 공개 전 같은 반 26명에게 참여 요청해 시드 확보(사용자 확정). 26명이 관심사를 고르면 첫 사용자가 빈 그래프를 보지 않는다 |
| 관찰 지표 | 시간대별 가입 수, 추천 0명 비율 추이 |

### R-12 알림 도달 실패

| 항목 | 내용 |
|---|---|
| 설명 | 사내 메신저 알림이 불가하고, 이메일은 안 보고, 브라우저 알림은 거부한다. 요청이 왔는지 모르면 수락도 재방문도 없다 |
| Likelihood | **High** |
| Impact | **High.** H4, H9 직접 타격 |
| 완화 | 온보딩에서 브라우저 알림 권유, 이메일 기본, 만료 전 리마인드, 앱 내 배지, 외부 채널(Discord 등) 등록(S3a, OQ-4a 확인 필요) |
| MVP 대응 | **필요.** OQ-4a(Discord 발송 가능성)는 Blocking에 가깝다 |
| 관찰 지표 | 채널별 클릭률, 만료율, 브라우저 허용률 |

### R-13 닉네임 사용자의 낮은 수락률

| 항목 | 내용 |
|---|---|
| 설명 | 닉네임으로 온 요청은 "누군지 몰라서" 수락되지 않는다. 닉네임/실명 공존 결정의 부작용 |
| Likelihood | Medium |
| Impact | Medium. 닉네임 사용자의 H3~H4 실패 |
| 완화 | 알림과 요청 상세에 판단 근거(관심사, 글, 메시지) 집중, 수락 시 실명 상호 공개로 위험 대칭 설명, 관찰 후 닉네임 사용자에게 실명 전환 권유 |
| MVP 대응 | 관찰. 닉네임/실명별 수락률을 반드시 분리 측정 |
| 관찰 지표 | 표시명 종류별 수락률 차이 |

### R-14 허위 실명 / 메신저에서 못 찾음

| 항목 | 내용 |
|---|---|
| 설명 | 실명 검증이 없으므로 오타나 허위 입력이 가능하다. 연결 후 메신저에서 못 찾으면 H5가 끊긴다 |
| Likelihood | Low (조직 내부, 형식 고정) |
| Impact | Medium |
| 완화 | "이름_캠퍼스_반" 형식 강제와 조합 미리보기, 후속 확인 "못 찾음" 사유 → 상대에게 먼저 연락 요청 알림 |
| MVP 대응 | 이미 반영 |
| 관찰 지표 | "못 찾음" 사유 비율 |

### R-15 차단 부재로 인한 안전 문제

| 항목 | 내용 |
|---|---|
| 설명 | 차단 기능을 두지 않기로 했다(사용자 결정). 불쾌한 요청을 반복해서 받는 사람이 스스로 끊을 수단이 없다 |
| Likelihood | Low (실명 조직, 2주, 재요청 14일 불가) |
| Impact | High (발생하면 개인에게 심각) |
| 완화 | 거절 후 14일 재요청 불가(사실상 MVP 내 1회), 신고 → 운영자 정지, 신고 접수 시 운영자 즉시 확인(일 단위) |
| MVP 대응 | 운영 대응. 운영자가 첫 2주 동안 신고를 매일 확인해야 한다. 심각 사례 1건이라도 나오면 차단 도입 재검토 |
| 관찰 지표 | 신고 건수, 동일인 대상 반복 신고 |

### R-16 운영자 부하

| 항목 | 내용 |
|---|---|
| 설명 | 관심사 제안, 신고, 게이트 판단, 병합/숨김을 운영자 한 명이 첫 2주 동안 매일 해야 한다 |
| Likelihood | Medium |
| Impact | Medium |
| 완화 | 운영 작업을 하루 1회 30분으로 묶기, 관리 UI 없이 데이터 직접 다루기(L6), 제안·신고를 한곳에 모으기 |
| MVP 대응 | 운영 계획으로 대응 |
| 관찰 지표 | 미처리 제안·신고 체류 시간 |

### R-17 2주 후 급감이 "실패"로 오해될 위험

| 항목 | 내용 |
|---|---|
| 설명 | 사용이 2주에 집중된다는 전제이므로 3주차 감소는 예상된 것이다. 이를 실패로 읽으면 잘못된 결정을 한다 |
| Likelihood | Medium |
| Impact | Medium (판단 오류) |
| 완화 | 판단 기준을 첫 2주 누적(North Star 40건, "대화 시작" 50%)으로 고정(14 §4~5). 3~4주는 잔존 관찰만 |
| MVP 대응 | 판단 기준 문서화로 대응. 이미 반영 |
