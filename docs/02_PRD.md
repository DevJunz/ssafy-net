## 1. Overview

### 1.1 Product Purpose

약 1,000명 규모 조직의 구성원이 관심사를 매개로 **아직 모르는 사람을 발견하고, 서로 대화할 의사를 확인한 뒤, 기존 조직 메신저에서 대화를 시작**하도록 돕는다.

### 1.2 Background

01_PRODUCT_BRIEF 2절 참조. 요약하면 조직에는 대화 도구는 있지만 "누구에게, 왜 말을 걸어도 되는지"를 알 수단이 없다.

### 1.3 Problem Statement

구성원은 (1) 자신과 관심사가 겹치는 사람이 조직 안에 있는지 알 수 없고, (2) 알게 되더라도 먼저 연락하는 비용이 높아 행동하지 않는다. 이 서비스는 발견 문제와 접근 비용 문제를 함께 해결한다.

## 2. Target User

### 2.1 Primary User

- 조직 구성원 전체. 특히 팀 밖 사람과 관심사 기반으로 교류하고 싶지만 먼저 나서기 부담스러운 사람.
- 조직 메신저를 매일 사용하며, 메신저에 실명으로 등록되어 있어 실명으로 서로를 찾을 수 있는 환경에 있다. MVP 대상은 단일 캠퍼스다.

### 2.2 사용 환경

- 업무용 PC 브라우저가 기본. 그래프 탐색은 넓은 화면을 전제로 설계한다.
- 모바일은 "받은 요청 확인과 수락/거절"만 가능하면 충분하다. 그래프 탐색의 모바일 대응은 MVP 범위 밖이다.

### 2.3 사용 상황

**사용 기간 전제**: 이 서비스는 공개 후 **약 2주 동안 사용이 집중되고 그 이후에는 크게 줄어들 가능성이 높다**(사용자 확인, 2026-09-07). 따라서 모든 시간 관련 정책(만료, 리마인드, 재안내, 후속 확인)은 "며칠"이 아니라 "하루 단위"로 짧게 잡고, 첫 2주 안에 사슬이 한 바퀴 돌도록 설계한다.

| 상황 | 빈도 | 사용자가 원하는 것 |
|---|---|---|
| 처음 가입해 관심사를 등록한 직후 | 1회 | "나와 비슷한 사람이 있긴 한가?" 확인 |
| 특정 주제로 이야기할 사람을 찾을 때 | 비정기 | 그 관심사를 가진 사람과 그들이 남긴 글 |
| 새로운 추천이나 요청 알림을 받았을 때 | 주 1~2회 | 빠르게 확인하고 수락/거절 |
| 심심할 때 탐색 | 초기에만 높음 | 예상 못한 사람 발견 |

네 번째 상황에 의존하는 설계는 하지 않는다. 재방문의 주된 동력은 세 번째 상황이어야 한다(H9).

## 3. Goals

### 3.1 Product Goal

- 관심사 그래프와 공통 관심사 기반 추천이 **실제 연결 요청과 수락**으로 이어지는지 검증한다.
- 연결이 성립된 쌍이 조직 메신저에서 대화를 시작하도록 충분한 Context를 제공한다.

### 3.2 User Goal

- 나와 관심사가 겹치는 사람을 이유와 함께 발견한다.
- 부담 없이 대화 의사를 표현하고 상대의 의사를 확인한다.
- 첫 대화를 시작할 소재를 얻는다.

### 3.3 Organization Goal

- 팀과 직급을 넘는 자발적 교류가 늘어난다.
- 운영자의 개입(행사 기획, 소개) 없이 교류가 발생한다.

---

## 4. Non-Goals

| Non-Goal | 이유 |
|---|---|
| **자체 메신저, DM, 그룹 채팅** | 조직 메신저가 존재한다. 서비스의 가치는 발견과 의사 확인에 있다 |
| 기존 관계 표시 (친구, 팔로우, 조직도) | 새로운 발견이 목적이며, 기존 관계는 그래프를 오염시킨다 |
| 피드, 댓글, 좋아요 중심의 커뮤니티 | 게시글은 Context 생성 수단이지 목적이 아니다 |
| 사람 이름 검색 | 이미 아는 사람을 찾는 기능은 Discovery 목적과 어긋난다 |
| 업무 역량 매칭, 프로젝트 인력 배치 | 관심사는 자발적 교류의 근거이지 평가 지표가 아니다 |
| 모바일 그래프 탐색 | 그래프는 넓은 화면 전제. 모바일은 요청 처리만 |
| 조직 외부 사용자 | 신뢰의 근거가 조직 소속이다 |
| 일정 조율, 만남 주선 | 메신저 이후는 사용자 몫이다 |

## 5. Core Features

기능은 세 가지 Discovery Loop에 매핑된다.

| # | Feature | Loop | 한 줄 정의 |
|---|---|---|---|
| F0 | Login / 신원 확인 | 전제 | 초대 링크로 들어와 간편 로그인하고, 실명을 입력하며, 표시명(닉네임 또는 실명)을 정한다 |
| F1 | Onboarding / Interest 선택 | 전제 | 프로필 확인 후 운영자 제공 목록에서 관심사를 고른다 |
| F2 | Interest Graph | Discover | 나를 중심으로 관심사와 사람의 관계를 탐색한다 |
| F3 | Person Focus | Understand | 사람을 선택하면 그 사람의 관심사와 나와의 공통점이 강조된다 |
| F4 | Interest Focus | Discover | 관심사를 선택하면 그 관심사를 가진 사람이 강조된다 |
| F5 | Person Profile | Understand | 사람의 공개 정보, 관심사, 나와 공통 관심사, 연결 상태를 본다 |
| F6 | Interest Post | Discover | 관심사별로 짧은 글을 남기고 읽는다 |
| F7 | Similar People | Discover | 공통 관심사가 기준 이상인 사람을 이유와 함께 추천받는다 |
| F8 | Similarity Edge | Understand | 나와 추천된 사람 사이에 공통 관심사 개수를 선으로 표시한다 |
| F9 | Connection Request | Connect | 짧은 메시지와 함께 대화 의사를 보낸다 |
| F10 | Connection Accept / Reject | Connect | 받은 요청을 수락하거나 거절한다 |
| F11 | Connections / Inbox | Connect | 받은 요청, 보낸 요청, 성립된 연결을 관리한다 |
| F11a | 연결 Action 안내 | Connect | 성립 시 누가 누구에게 먼저 연락할지를 구체적으로 지시한다 |
| F12 | Network Recommendation | Network | 여러 관심사를 함께 공유하는 소규모 그룹을 추천받는다 |
| F13 | Network Participation | Network | 추천된 그룹에 참여 의사를 밝히고, 성립되면 멤버와 Context를 확인한다 |
| F14 | Notification | 재방문 | 받은 요청, 수락, 새 추천을 알린다 |
| F15 | Report | 안전 | 특정 사용자나 글을 운영자에게 신고한다 |
| F16 | Interest 제안 | 전제 | 원하는 관심사가 없을 때 운영자에게 제안한다 |

MVP 포함 여부는 03_MVP_SCOPE에서 정한다.

## 6. Functional Requirements

각 요구사항은 "사용자는 ~할 수 있어야 한다" 또는 "시스템은 ~해야 한다"로 쓴다. 우선순위는 03_MVP_SCOPE를 따른다.

### FR-0. 로그인 / 신원

- FR-0.1 사용자는 별도 비밀번호 없이 **Google 계정**으로 로그인할 수 있어야 한다(MVP는 Google만. 사용자 확정, 2026-09-07). 다른 계정은 Later.
- FR-0.2 가입은 **초대 링크를 통해서만** 가능하다. MVP에서는 운영자가 조직 내부에 공유하는 링크 하나로 충분하며, 소속은 별도 검증 없이 사용자를 신뢰한다. 서비스가 여러 조직으로 확장되면 조직별 권한자가 발급하는 초대 링크/초대장으로 가입하는 구조가 된다(Later). 초대 링크 없이 들어온 사용자는 가입할 수 없다.
- FR-0.3 소셜 계정의 이름은 실명이 아닐 수 있으므로, 온보딩에서 **사내 메신저에 등록된 실명**을 입력하는 단계가 있어야 한다. 실명은 연결 성립 시 상대에게 공개되므로 정확해야 함을 이 시점에 안내한다. 형식은 사내 메신저 표시명과 같은 **"이름_캠퍼스_반"**(예: 최준환_서울_18반)이다. 이름과 반을 따로 입력받아 이 형식으로 조합한다. 반은 실명의 일부이므로 연결 전에는 보이지 않는다.
- FR-0.4 사용자는 연결 전 다른 사람에게 보일 **표시명**을 정한다. **닉네임과 실명 중 선택**할 수 있다. 실명을 표시명으로 쓰는 사용자는 연결 전에도 실명이 보인다. 어느 쪽이든 **연결 성립 시에는 실명이 공개**된다. 표시명 규칙(실명 사용자와 혼동되는 닉네임 금지, 중복 처리, 부적절 표현)은 12_PRIVACY에서 정한다.
- FR-0.5 표시명이 실명인지 닉네임인지 다른 사용자가 구분할 수 있어야 한다. 실명 사용자에게는 표시가 붙는다.

### FR-1. Onboarding / Interest 선택

- FR-1.1 사용자는 최초 진입 시 프로필(실명, 표시명)을 확인하고 무엇이 언제 공개되는지 볼 수 있어야 한다. **연결 전에는 표시명과 관심사만 공개**되고, **실명은 연결 성립 시 양쪽에 동시에 공개**된다(12_PRIVACY 참조). 소속 정보는 단일 캠퍼스 대상이므로 표시하지 않는다.
- FR-1.2 사용자는 운영자가 제공한 Category별 Interest 목록에서 관심사를 선택할 수 있어야 한다. 목록 내 검색(필터)이 가능해야 한다.
- FR-1.3 시스템은 최소 `[P-01]`개 미만이면 완료를 막고, 최대 `[P-02]`개를 초과하면 선택을 막아야 한다. 이유를 화면에서 설명해야 한다.
- FR-1.4 사용자는 관심사를 언제든 수정할 수 있어야 한다. 수정 즉시 그래프와 추천에 반영된다.
- FR-1.5 사용자는 원하는 관심사가 없을 때 이름을 적어 제안할 수 있어야 한다. 제안은 즉시 그래프에 나타나지 않는다.
- FR-1.6 관심사 선택을 마치기 전에는 그래프와 추천에 진입할 수 없어야 한다. 관심사 없는 사용자는 다른 사람에게도 보이지 않는다.

### FR-2. Interest Graph

- FR-2.1 기본 그래프는 **전체 조직이 아닌 사용자 중심의 부분 그래프**여야 한다. 내 관심사, 그 관심사를 가진 사람 중 나와 관련이 높은 사람, 그들의 관심사를 보여준다. 1,000명 전체를 한 화면에 그리지 않는다.
- FR-2.2 Interest 노드는 Person 노드보다 시각적으로 크고, 이름이 항상 보여야 한다.
- FR-2.3 사용자는 그래프를 이동, 확대, 축소할 수 있어야 한다.
- FR-2.4 사용자는 그래프에서 관심사를 골라 그 관심사 주변으로 탐색 범위를 옮길 수 있어야 한다(Interest Focus를 통해).
- FR-2.5 그래프에 표시되는 사람 수와 선 수에는 상한이 있어야 한다. 상한을 넘으면 관련도 순으로 잘라내고, 잘렸다는 사실을 사용자에게 알린다.
- FR-2.6 아무것도 선택하지 않은 상태에서 그래프는 "무엇을 클릭하면 되는지"를 안내해야 한다.

### FR-3. Person Focus

- FR-3.1 사람을 선택하면 그 사람과 그 사람의 관심사만 강조되고 나머지는 흐려져야 한다.
- FR-3.2 나와 공통인 관심사는 공통이 아닌 관심사와 구분되어 보여야 한다.
- FR-3.3 선택과 동시에 Person Profile(FR-5)이 열려야 한다.

### FR-4. Interest Focus

- FR-4.1 관심사를 선택하면 그 관심사를 가진 사람들만 강조되어야 한다.
- FR-4.2 강조되는 사람 수가 상한을 넘으면 나와 공통 관심사가 많은 순으로 우선 표시하고 나머지는 목록에서 볼 수 있어야 한다.
- FR-4.3 선택과 동시에 Interest 상세(사람 수, 사람 목록, 게시글)가 열려야 한다.

### FR-5. Person Profile

- FR-5.1 표시명(실명 여부 표시 포함), 관심사 목록, 나와 공통 관심사와 개수, 현재 연결 상태(없음/요청 보냄/요청 받음/연결됨)를 보여야 한다. 연결된 사람은 실명이 함께 보인다.
- FR-5.2 연결 상태에 따라 가능한 행동(요청 보내기, 수락/거절, 메신저에서 찾기)만 노출해야 한다.
- FR-5.3 그 사람이 쓴 게시글이 있으면 최근 글 일부를 보여줘야 한다(F6 포함 시).
- FR-5.4 자기 자신의 프로필에서는 연결 행동이 없어야 한다.

### FR-6. Interest Post

- FR-6.1 해당 관심사를 선택한 사용자만 그 관심사에 글을 쓸 수 있어야 한다.
- FR-6.2 글은 짧은 텍스트 한 덩어리다. 제목, 댓글, 좋아요, 이미지는 없다.
- FR-6.3 작성자는 자기 글을 삭제할 수 있어야 한다. 수정은 삭제 후 재작성으로 대신한다.
- FR-6.4 글은 관심사 상세와 작성자 프로필에서 보여야 한다. 전체 피드는 없다.
- FR-6.5 글에서 작성자를 눌러 Person Profile로 이동할 수 있어야 한다. 글의 존재 이유는 이 이동이다.
- FR-6.6 글이 없는 관심사에는 "이 관심사로 이야기하고 싶은 것을 남겨보세요"처럼 작성을 유도하는 빈 상태가 있어야 한다.

### FR-7. Similar People

- FR-7.1 사용자는 나와 공통 관심사가 `[P-03]`개 이상인 사람의 목록을 볼 수 있어야 한다. 정렬은 공통 관심사 개수 내림차순이며, 동점이면 희소한 관심사를 공유하는 쪽이 앞선다(13_RECOMMENDATION_PRINCIPLES 참조).
- FR-7.2 모든 추천에는 공통 관심사 목록과 개수가 함께 보여야 한다. 이유 없는 추천은 없다.
- FR-7.3 이미 연결된 사람, 요청이 오간 사람은 추천에서 별도 표시되어야 한다(09_CONNECTION_POLICY).
- FR-7.4 추천 결과가 없으면 관심사를 늘리거나 바꾸도록 안내해야 한다.
- FR-7.5 추천 목록에서 사람을 누르면 그래프의 해당 사람이 강조되고 Person Profile이 열려야 한다.

### FR-8. Similarity Edge

- FR-8.1 Similar People 모드에서는 나와 추천된 사람 사이에 선이 그려지고, 선 위에 공통 관심사 개수가 보여야 한다.
- FR-8.2 선을 가리키거나 누르면 공통 관심사 이름이 보여야 한다.
- FR-8.3 이 선은 "현재 관심사가 겹친다"는 뜻이지 "아는 사이"가 아니라는 점이 화면에서 설명되어야 한다.
- FR-8.4 모드를 끄면 선이 사라지고 그래프가 원래 상태로 돌아가야 한다.

### FR-9. Connection Request

- FR-9.1 사용자는 다른 사람에게 짧은 메시지와 함께 연결 요청을 보낼 수 있어야 한다. 메시지는 필수이며 길이에 상한이 있다.
- FR-9.2 요청 화면에는 공통 관심사가 미리 보여 메시지 작성의 소재가 되어야 한다.
- FR-9.3 자기 자신, 이미 연결된 사람, 요청이 진행 중인 사람, 재요청 대기 중인 사람에게는 보낼 수 없어야 한다.
- FR-9.4 하루/주간 요청 횟수에 상한 `[P-06]`이 있어야 한다.
- FR-9.5 보낸 요청은 상대가 처리하기 전까지 취소할 수 있어야 한다.

### FR-10. Connection Accept / Reject

- FR-10.1 받은 요청에는 보낸 사람의 프로필 요약, 공통 관심사, 메시지가 함께 보여야 한다.
- FR-10.2 수락하면 양쪽 모두 "연결됨" 상태가 되고, **서로의 실명이 동시에 공개**된다. 닉네임 사용자의 수락 버튼 근처에는 "수락하면 내 실명이 상대에게 공개됩니다"가 보여야 한다.
- FR-10.3 거절하면 보낸 사람에게는 거절 사실이 직접 통보되지 않는다. 보낸 요청 목록에서 "응답 없음"으로 보인다. 표시 시점은 거절 후 **최대 하루**다. 보낸 사람이 오래 기다리지 않게 하되, 즉시 표시로 거절을 확신하게 하지는 않는다.
- FR-10.4 거절 후 재요청 가능 여부와 대기 기간은 `[P-07]`을 따른다.
- FR-10.5 요청은 `[P-08]`일 동안 응답이 없으면 만료된다.

### FR-11. Connections / Inbox

- FR-11.1 사용자는 받은 요청, 보낸 요청, 성립된 연결을 각각 목록으로 볼 수 있어야 한다.
- FR-11.2 성립된 연결에는 상대의 실명(메신저 표시명 형태), 공통 관심사, 요청 당시 메시지가 남아 있어야 한다. 이것이 메신저에서 첫 대화를 시작할 Context다.
- FR-11.3 **연결 Action 안내**: 성립 화면은 "누가, 누구에게, 무엇을" 해야 하는지 구체적으로 지시해야 한다. 1:1에서는 **요청을 보낸 사람이 시작자**다. 예: "민수님, 사내 메신저에서 김지수님을 찾아 첫 메시지를 보내주세요." 받은 사람에게는 "민수님이 먼저 연락할 예정입니다"를 보여준다. 조직 메신저의 사용자 링크를 열 수 있으면 연다.
- FR-11.4 성립 화면은 첫 메시지의 소재(공통 관심사, 요청 메시지, 상대의 최근 글)를 함께 보여줘야 한다. 메시지 문안을 대신 써주지는 않는다.
- FR-11.5 시작자가 `[P-11]`일 안에 "대화를 시작했다"고 표시하지 않으면, 상대에게 "아직 연락이 없다면 먼저 연락해도 좋습니다"를 안내한다.
- FR-11.6 연결 성립 후 `[P-18]` 2일에 양쪽에 "대화를 시작하셨나요?"를 한 번 물을 수 있어야 한다. 이 응답은 H5 검증의 유일한 신호다.

### FR-12. Network Recommendation

- FR-12.1 시스템은 멤버 전원이 `[P-04]`개 이상의 관심사를 공유하는 `[P-05]`명 규모의 그룹 후보를 만들어 각 멤버에게 추천해야 한다.
- FR-12.2 추천에는 멤버 목록, 전원 공통 관심사, 멤버 수가 함께 보여야 한다.
- FR-12.3 그래프에서 해당 그룹만 강조해 볼 수 있어야 한다. 이때 선의 수가 과도하지 않아야 한다(NFR-2).
- FR-12.4 같은 사람에게 비슷한 구성의 그룹이 반복 추천되지 않아야 한다.
- FR-12.5 추천 후보가 없으면 그 사실과 이유(관심사를 더 고르면 생길 수 있음 등)를 보여야 한다.

### FR-13. Network Participation

- FR-13.1 각 멤버는 참여 또는 거절을 선택할 수 있어야 한다. 자동 참여는 없다.
- FR-13.2 `[P-09]`명 이상이 참여를 선택하면 Network가 성립한다. 거절한 사람은 제외되고 성립 후에는 멤버로 보이지 않는다.
- FR-13.3 성립되면 참여 멤버 전원에게 멤버 목록(실명), 공통 관심사가 공개된다.
- FR-13.3a **Network 연결 Action 안내**: 시스템은 시작자 한 명을 지정하고 전원에게 알린다. 시작자는 **가장 먼저 참여(연결하기) 버튼을 누른 사람**이다. 예: "주영님이 사내 메신저에서 김민수님, 이지수님을 초대해 대화를 시작해주세요." 나머지에게는 "주영님이 초대할 예정입니다"를 보여준다. 초대할 실명 목록은 한 번에 복사할 수 있어야 한다.
- FR-13.3b 시작자가 `[P-11]`일 안에 시작을 표시하지 않으면 나머지 멤버에게 "누구든 먼저 초대해도 좋습니다"를 안내한다.
- FR-13.4 성립되지 않은 추천은 `[P-10]`일 후 만료되고, 만료 사실이 참여를 선택했던 사람에게 알려진다.
- FR-13.5 참여를 선택했지만 아직 성립 전인 상태가 사용자에게 명확히 보여야 한다.

### FR-14. Notification

웹 서비스는 사용자가 열어야만 보인다. 요청을 받은 사실을 모르면 수락이 일어나지 않으므로, 알림은 "사용자가 이미 있는 곳"에 도착해야 한다.

- FR-14.1 **채널**: 사내 메신저로는 알림을 보낼 수 없다(확인됨). 따라서 (1) **이메일** — 전원에게 보장되는 기본 채널. 즉시 알림용. (2) **브라우저 알림** — 사용자가 허용한 경우 즉시성을 높이는 보조 채널. 온보딩 마지막에 허용을 한 번 권하되 강요하지 않는다. (3) **사용자 등록 외부 채널** — Discord, KakaoTalk 등 사용자가 직접 등록한 곳으로 알림. 채널마다 개인 대상 발송 가능 여부와 등록 절차가 다르므로 채널별로 가능성을 확인한 뒤 추가한다(OQ-4a). (4) **앱 내 알림함** — 항상 존재한다.
- FR-14.2 **즉시 알림과 묶음 알림을 구분**한다. 즉시: 받은 요청, 요청 수락, Network 성립, Network 시작자 지정. 묶음(주 1회): 새 Similar People, 관심 있는 Interest의 새 글, Network 추천. 묶음은 사용자가 끌 수 있다.
- FR-14.3 알림에는 **판단 근거가 포함**되어야 한다. 받은 요청 알림이면 보낸 사람 닉네임, 공통 관심사 개수와 이름, 메시지 첫 줄. 사용자가 앱을 열기 전에 "볼 가치가 있는지"를 알 수 있어야 한다.
- FR-14.4 알림은 한 번의 이동으로 행동 화면(해당 요청의 수락/거절, 성립된 연결의 Action 안내)에 도착해야 한다. 홈으로 보내고 다시 찾게 하지 않는다.
- FR-14.5 사용자는 채널별로 알림을 켜고 끌 수 있어야 한다. 단, 받은 요청 알림은 최소 한 채널에서는 켜져 있어야 한다.
- FR-14.6 같은 사건으로 여러 채널에 중복 알림을 보내지 않는다. 앱 안에서 이미 확인한 사건은 외부 알림을 보내지 않는다.

### FR-15. Report

- FR-15.1 사용자는 사람, 요청 메시지, 글을 신고할 수 있어야 하며 운영자가 확인할 수 있어야 한다.
- FR-15.2 차단 기능은 **제공하지 않는다**(사용자 결정, 2026-09-07). 원치 않는 접근은 거절(재요청 14일 불가), 요청 횟수 상한, 신고로 막는다. 운영자는 신고가 누적된 사용자의 요청 권한을 정지할 수 있어야 한다.

### FR-16. Interest 제안 / 운영

- FR-16.1 운영자는 관심사 목록과 Category를 준비하고 추가, 이름 변경, 병합, 숨김을 할 수 있어야 한다.
- FR-16.2 사용자의 제안은 운영자에게 모여야 하며, 채택 여부가 제안자에게 알려져야 한다.
