## 1. 서비스 한 줄 정의

> 약 1,000명 규모 조직 안에서, **관심사 그래프를 통해 아직 모르는 사람을 발견하고 서로 대화할 의사를 확인한 뒤, 실제 대화는 기존 메신저로 넘기는** 네트워킹 서비스.

역할은 세 단어로 요약된다. **Discover, Understand, Connect.** 대화(Conversation)는 서비스 밖에서 일어난다.

---

## 2. Background

- 1,000명 규모 조직은 "이름은 들어봤지만 무엇에 관심 있는지 모르는 사람"이 대부분인 크기다. 150명 이하 조직처럼 자연스럽게 서로를 알게 되지 않고, 수만 명 조직처럼 공식적인 커뮤니티 운영 조직이 있지도 않다.
- 조직에는 이미 메신저가 있다. 대화 도구는 문제가 아니다. 문제는 **누구에게 말을 걸어야 하는지, 왜 걸어도 되는지**를 알 방법이 없다는 것이다.
- 기존 대안은 모두 한계가 있다.
  - 메신저 채널: 이미 그 주제에 들어온 사람만 보인다. 새로운 발견이 없다.
  - 프로필 태그 검색: 검색어를 아는 사람만 찾을 수 있고, "나와 겹치는 정도"를 보여주지 않는다.
  - 오프라인 네트워킹 행사: 빈도가 낮고 우연에 의존한다.
- Phase 0 프로토타입에서 다음이 확인되었다.
  - 관심사–사람 그래프의 형태와 Focus 인터랙션은 사용자가 의도한 모습과 일치한다.
  - 공통 관심사 개수를 사람–사람 선으로 보여주는 표현은 자연스럽다.
  - 여러 관심사를 함께 공유하는 소규모 그룹을 추천하는 개념은 유효하다. 단, 선이 많아지면 가독성이 떨어진다.
  - 연결 요청에는 짧은 메시지가 함께 가야 한다.

---

## 3. Problem

**조직 구성원은 자신과 관심사가 겹치는 사람이 조직 안에 있다는 것을 알 방법이 없고, 알게 되더라도 먼저 말을 거는 비용이 너무 높다.**

이 문제는 두 층으로 나뉜다.

1. **발견 문제 (Discovery)**: 나와 비슷한 사람이 누구인지, 어디에 있는지 보이지 않는다.
2. **접근 문제 (Approach Cost)**: 발견하더라도 "왜 나에게 연락했는지"를 설명해야 하는 부담과 거절당할 위험 때문에 행동하지 않는다.

발견만 해결하면 "재미있는 지도"로 끝난다. 접근 비용까지 낮춰야 실제 관계로 이어진다. 이 서비스는 두 문제를 모두 다룬다.

---

## 4. Target User

### Primary User

- 조직에 소속되어 있고 조직 메신저를 일상적으로 사용하는 구성원
- 팀 밖의 사람과 관심사 기반으로 교류하고 싶지만, 먼저 나서기는 부담스러운 사람
- 예: 사이드 프로젝트 동료, 스터디 멤버, 취미 동호인, 같은 기술을 쓰는 다른 팀 사람을 찾고 싶은 사람

### Secondary User

- 조직 운영자: 구성원 간 교류를 촉진하고 싶지만 행사 외에는 수단이 없는 사람. MVP에서는 관심사 목록 관리자 역할로만 등장한다.

### 명시적으로 타깃이 아닌 사용자

- 이미 아는 사람과의 관계를 관리하고 싶은 사람
- 조직 밖 사람과 네트워킹하려는 사람

---

## 5. User Pain Point

| # | Pain Point | 현재 대응 | 왜 해결되지 않는가 |
|---|---|---|---|
| P1 | 나와 관심사가 겹치는 사람이 조직 안에 있는지조차 모른다 | 우연한 대화, 행사 | 빈도가 낮고 운에 의존 |
| P2 | 특정 주제로 이야기할 사람을 찾을 방법이 없다 | 메신저 전체 공지, 채널 검색 | 공개적으로 묻는 부담이 크고 응답률이 낮음 |
| P3 | 먼저 연락할 명분이 없다 | 소개를 통해 접근 | 소개해 줄 사람이 없으면 막힘 |
| P4 | 1:1은 부담스럽고, 큰 모임은 겉돌게 된다 | 동호회 가입 | 규모가 크고 이미 형성된 관계에 끼어들어야 함 |
| P5 | 상대가 나와 대화할 의사가 있는지 모른 채 연락해야 한다 | 없음 | 거절 위험을 개인이 전부 감수 |

P3와 P5가 이 서비스의 차별점이다. 대부분의 대안은 P1, P2(발견)만 다룬다.

## 6. Product Vision

> 조직 안의 누구든, 자신의 관심사를 등록하는 것만으로 **"이 사람과는 이런 이야기를 할 수 있겠다"**를 알게 되고, 서로 의사를 확인한 상태에서 부담 없이 첫 대화를 시작할 수 있다.

서비스가 성공한 상태는 "그래프를 많이 본다"가 아니라 **"새로운 사람과 서로 연결 의사를 확인한 쌍(또는 그룹)이 매주 생긴다"**이다.

---

## 7. Core Value Proposition

| 가치 | 사용자가 얻는 것 | 대체재 대비 차이 |
|---|---|---|
| **Explainable Discovery** | 나와 관심사가 겹치는 사람을 "왜 겹치는지"와 함께 발견 | 태그 검색은 겹침의 정도와 이유를 보여주지 않음 |
| **Consent Before Contact** | 상대가 대화 의사를 밝힌 뒤에 연락 | 메신저 DM은 일방적 접근 |
| **Ready-made Context** | 공통 관심사와 최근 글이 첫 대화의 소재가 됨 | "안녕하세요, 저는…"부터 시작해야 하는 부담 제거 |
| **Small Group Start** | 3~5명 규모의 관심사 공유 그룹을 추천 | 1:1의 부담과 대형 모임의 소외 사이 |

### 그래프여야 하는 이유에 대한 PM 검토

그래프는 이 서비스의 핵심 표현이지만, 모든 기능이 그래프여야 하는 것은 아니다.

- 그래프가 우위인 곳: **탐색과 이해**. 내가 검색어를 모르는 상태에서 인접한 관심사와 사람을 발견하는 것, 어떤 사람이 왜 나와 관련 있는지 한눈에 이해하는 것.
- 리스트가 우위인 곳: **행동과 관리**. 추천 목록 확인, 요청 보내기, 받은 요청 처리, 연결 목록.

따라서 그래프는 "Discover와 Understand의 도구"로 위치시키고, Connect 이후의 관리 화면은 리스트로 설계한다. 그래프 자체가 재방문 이유가 될 것이라는 기대는 하지 않는다(H7, Risk: Graph Novelty).

## 8. 해결하지 않는 문제

| 하지 않는 것 | 이유 |
|---|---|
| 자체 메신저, DM, 그룹 채팅 | 조직에 메신저가 이미 있다. 핵심 가치는 대화가 아니라 발견과 의사 확인이다 |
| 이미 아는 사람과의 관계 관리 (친구 목록, 팔로우) | 서비스의 목적은 새로운 발견이다. 기존 관계 표시는 그래프를 오염시킨다 |
| 일반 커뮤니티/SNS (피드, 좋아요, 댓글 확장) | 게시글은 네트워킹 Context 생성 수단이지 목적이 아니다 |
| 업무 협업 도구 (프로젝트 매칭, 인력 배치) | 관심사는 자발적 교류의 근거이지 업무 역량 지표가 아니다 |
| 조직 외부 사용자 | 신뢰 기반이 조직 소속에서 나온다 |
| 실제 만남/일정 조율 | 메신저로 넘어간 뒤의 일은 사용자 몫이다 |

## 9. 주요 Product Hypothesis

각 가설은 아직 검증되지 않았다. Phase 0은 **이해 가능성**을 확인했을 뿐 **행동**을 확인하지 않았다. 상태는 모두 `Unvalidated`이며, 17_ASSUMPTION_REGISTER에서 추적한다.

| ID | 가설 | 근거 | 반증되면 |
|---|---|---|---|
| **H1** | 사용자는 온보딩에서 자신을 설명하기에 충분한 수의 관심사를 스스로 등록한다 | 운영자 제공 목록 100개, 선택만 하면 됨 | 그래프가 희소해지고 모든 추천이 무의미해짐. 서비스 전체의 전제 |
| **H2** | 공통 관심사 개수는 "이 사람과 이야기해볼 만하다"를 판단하는 데 충분한 신호다 | Phase 0에서 공통 개수 표시가 직관적이라고 확인 | 추천 기준을 관심사 외 신호(글, 활동)로 확장해야 함 |
| **H3** | 추천 이유와 짧은 메시지가 있으면 사용자는 모르는 사람에게 연결 요청을 실제로 보낸다 | P3, P5 해소. Phase 0 피드백에서 메시지 동봉 요청 | 발견까지만 되고 행동이 없음. 접근 비용을 더 낮추는 장치 필요 |
| **H4** | 요청을 받은 사람은 공통 관심사가 보이면 높은 비율로 수락한다 | 조직 내부라는 신뢰 기반, 추천 이유 노출 | 수락률이 낮으면 요청 보낸 사람의 이탈로 이어짐 |
| **H5** | 연결이 수락되면 사용자는 실제로 조직 메신저에서 대화를 시작한다 | 서로 의사 확인 완료, 대화 소재(공통 관심사) 제공 | 서비스 안에서만 끝나는 "형식적 연결"이 됨. 성립 이후 Context 제공을 강화해야 함 |
| **H6** | 3~5명이 5개 이상 관심사를 공유하는 그룹 추천은 1:1과 다른 가치를 준다 | P4. 1:1보다 낮은 부담, 대형 모임보다 높은 밀도 | Network 기능을 Later로 이동. 1:1에 집중 |
| **H7** | 그래프 탐색은 리스트/검색보다 "예상하지 못한 사람"의 발견을 더 많이 만든다 | 인접 관심사를 따라가는 탐색은 리스트로 재현하기 어려움 | 그래프를 Understand(추천 이유 시각화) 용도로 축소하고 탐색은 리스트 우선 |
| **H8** | 관심사별 게시글은 "누가 활동하는지"를 드러내 사람 발견의 계기가 된다 | Phase 0에서 그래프 옆 게시글이 자연스럽다고 확인 | 게시글이 커뮤니티로 변질되거나 아무도 쓰지 않음. 기능 축소 또는 제거 |
| **H9** | 사용자는 새로운 추천이나 받은 요청이 있을 때 재방문한다 (그래프 자체는 재방문 이유가 아니다) | 네트워킹 서비스의 재방문은 "나에게 온 것"이 만든다 | 알림/다이제스트 없이는 1회성 사용에 그침 |

### 가설 간 의존 관계

```
H1 (관심사 등록)
 └→ H2 (공통 관심사가 신호)
     ├→ H3 (요청 발송) → H4 (수락) → H5 (메신저 이동)
     ├→ H6 (그룹 추천 가치)
     └→ H7 (그래프 탐색 가치)
H8 (게시글) ── H2를 보강
H9 (재방문) ── H3~H6 전체의 지속성
```

H1과 H2가 무너지면 나머지는 검증할 필요가 없다. MVP는 **H1, H2, H3, H4, H5**를 검증하는 데 우선순위를 둔다. H6, H7, H8은 이 다섯이 성립한 뒤에 의미가 있다.

## 10. PM 비판 노트

기획자로서 현재 아이디어에 남기는 반론이다. 이후 단계에서 답해야 한다.

1. **"수락 후 메신저에서 실제로 대화가 시작되는가"(H5)가 가장 약한 고리다.** 서비스는 여기서 손을 떼지만, 성공 정의는 여기에 달려 있다. → Step 2~4에서 시작자 지정과 Action 안내(FR-11.3)로 답했다. 문안 자동 생성은 Later(L5).
2. **게시글(H8)은 핵심 가치를 강화하는지 아직 불확실하다.** 글이 없으면 빈 게시판이 그래프 옆에 붙어 있게 되고, 글이 많으면 커뮤니티로 변질된다. Step 2에서 Must Have인지 Should Have인지 냉정하게 판단한다.
3. **Network 추천(H6)은 1:1보다 성립 조건이 훨씬 까다롭다.** 3명 이상의 동시 수락이 필요하다. 1,000명 규모에서 실제로 성립하는 Network가 주당 몇 개인지 추정한 뒤 MVP 포함 여부를 정한다.
4. **그래프의 Hairball 문제는 Phase 0에서 이미 관찰되었다.** 사람 25명, 관심사 15개에서도 Network 모드의 선이 많았다. 1,000명, 100개 관심사에서는 전체 그래프를 한 번에 보여주는 것 자체가 불가능하다. "전체 그래프"가 아닌 "나를 중심으로 한 부분 그래프"가 기본 화면이어야 한다는 방향으로 Step 3~4에서 재검토한다.
5. **Popular Interest 문제.** "백엔드"처럼 절반이 선택하는 관심사는 공통 관심사 개수를 부풀린다. 공통 개수만으로 추천하면 흔한 관심사를 많이 고른 사람이 항상 상위에 온다. 추천 기준에 희소성 가중을 둘지 Step 5의 정책에서 다룬다.

## 11. Step 1 결정 사항 / 미결정 사항

### 결정됨

- 서비스 정의: Discover → Understand → Connect. 대화는 외부 메신저.
- 해결 문제: 발견 문제와 접근 비용 문제를 모두 다룬다.
- Primary User: 팀 밖 사람과 관심사 기반 교류를 원하지만 먼저 나서기 부담스러운 조직 구성원.
- Non-Goal: 자체 메신저, 기존 관계 관리, 일반 커뮤니티, 업무 매칭, 외부 사용자.
- 그래프의 역할: Discover와 Understand의 도구. Connect 이후 관리는 리스트.
- 연결 요청에는 짧은 메시지가 동봉된다 (Phase 0 피드백 반영).
- MVP 검증 우선순위: H1, H2, H3, H4, H5.
- (Step 2 추가) 표시명은 닉네임/실명 선택제. 연결 성립 시 양쪽 실명("이름_캠퍼스_반") 상호 공개. 소속은 표시하지 않는다. 메신저에서는 실명으로 찾는다.
- (Step 2 추가) 연결 성립 시 시작자를 지정해 "누가 누구에게 먼저 연락할지"를 안내한다. H5 보강 장치.
- (Step 2 추가) 외부 채널 즉시 알림은 필수다. 웹 서비스는 열어야만 보이기 때문이다.
