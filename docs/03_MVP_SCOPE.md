## 1. MVP가 검증하려는 것

> **관심사 그래프와 공통 관심사 기반 추천이, 아직 모르는 사람에 대한 실제 연결 요청과 수락으로 이어지는가.**

01_PRODUCT_BRIEF의 가설 중 **H1 → H2 → H3 → H4 → H5** 사슬이 검증 대상이다. 이 다섯이 성립하지 않으면 Network(H6), 그래프 탐색 우위(H7), 게시글(H8)은 검증할 의미가 없다.

따라서 MVP의 Must Have는 **"관심사 등록 → 발견 → 이유 이해 → 요청 → 수락 → 메신저 이동"** 한 줄이 끊기지 않는 데 필요한 것으로만 구성한다.

---

## 2. 분류 원칙

| 등급 | 기준 |
|---|---|
| **Must Have** | 이것이 없으면 H1~H5 사슬이 끊기거나, 없이는 조직에 배포할 수 없다(안전, 프라이버시) |
| **Should Have** | 사슬을 강화하거나 H6~H9를 검증한다. MVP 기간 안에 넣되, 일정이 밀리면 뺀다 |
| **Later** | MVP 검증 결과가 나온 뒤에 판단한다. 지금 넣으면 검증을 흐린다 |

"있어 보이는가"는 기준이 아니다. Phase 0에서 승인된 기능이라도 사슬에 필요 없으면 Should 이하로 내린다.

## 3. 기능 분류

### 3.1 Must Have

| # | 기능 | 왜 MVP에 필요한가 |
|---|---|---|
| M0 | 간편 로그인 + 초대 링크 가입 + 실명 입력 + 표시명(닉네임/실명) 선택 (F0) | 초대 링크가 조직 경계다. 실명이 정확하지 않으면 연결 후 메신저에서 찾을 수 없어 H5가 끊긴다 |
| M1 | 프로필 확인 + 관심사 선택 온보딩 (F1) | 관심사가 없으면 그래프도 추천도 없다. H1의 검증 자체 |
| M2 | 사용자 중심 Interest Graph (F2) | 서비스의 정체성이자 Discover의 도구. 단, 전체 그래프가 아닌 나 중심 부분 그래프로 한정 |
| M3 | Person Focus (F3) | "왜 이 사람이 나와 관련 있는가"를 보여주는 Understand의 핵심 |
| M4 | Interest Focus (F4) | 관심사에서 사람으로 가는 Discovery Loop의 시작점 |
| M5 | Person Profile with 공통 관심사 (F5) | 요청 전에 상대를 이해하는 화면. 요청 버튼이 여기 있다 |
| M6 | Similar People 목록 + 추천 이유 (F7) | H2, H3 검증의 직접 수단. 그래프 없이도 이것만으로 요청이 발생하는지 본다 |
| M7 | Similarity Edge (F8) | 추천 이유를 그래프 위에서 보여주는 장치. 이것이 없으면 그래프는 추천과 분리된 장식이 된다. H7의 최소 검증 |
| M8 | Connection Request with 메시지 (F9) | H3의 검증 수단. Phase 0 피드백으로 메시지 동봉 확정 |
| M9 | Accept / Reject (F10) | H4의 검증 수단 |
| M10 | Connections / Inbox + 실명 공개 (F11) | 수락 후 메신저로 넘어가는 유일한 통로. 이것이 없으면 H5는 검증 불가 |
| M10a | 연결 Action 안내: 시작자 지정, 상대 실명, 첫 메시지 소재 (F11a) | 수락 후 "누가 먼저 연락하는가"가 정해지지 않으면 양쪽 모두 기다린다. H5의 가장 약한 고리를 직접 보강하는 장치 |
| M11 | 알림: 앱 내 알림함 + 이메일 즉시 알림 + 브라우저 알림(허용 시) (F14) | 웹 서비스는 열어야만 보인다. 요청이 왔음을 외부에서 알려주지 않으면 수락(H4)도 재방문(H9)도 일어나지 않는다. 사내 메신저 알림은 불가하므로 이메일이 기본, 브라우저 알림이 즉시성 보조 |
| M13 | 운영자 관심사 목록 준비 (F16 일부) | 초기 100개 목록이 있어야 온보딩이 가능. 관리 UI는 필요 없고 목록 자체가 필요 |
| M14 | 연결 후 후속 확인 "대화를 시작하셨나요?" (FR-11.4) | 대화가 외부에서 일어나므로 H5를 측정할 유일한 신호. 질문 하나이지만 없으면 MVP의 성공 여부를 알 수 없다 |

### 3.2 Should Have

| # | 기능 | 왜 Must가 아닌가 | 왜 MVP 안에 넣고 싶은가 |
|---|---|---|---|
| S1 | Interest Post (F6) — 짧은 글, 댓글/좋아요 없음 | H1~H5 사슬에 없어도 요청은 발생한다. 초기에 글이 없으면 빈 화면이 그래프 옆에 붙는다 | H8 검증. "이 관심사에서 누가 활동하는가"를 보여줘 Interest Focus에서 사람을 고르는 이유가 된다 |
| S2 | Network Recommendation + Participation (F12, F13) | 3명 이상 동시 수락이 필요해 1:1보다 성립이 훨씬 어렵다. 실제 관심사 분포를 보기 전에는 후보가 몇 개 나올지 모른다 | H6 검증. Phase 0에서 개념 승인됨. 1:1과 다른 가치(P4)를 준다면 서비스의 차별점이 된다 |
| S3 | 묶음 알림(새 추천, 새 글 주간 다이제스트) (F14 일부) | 즉시 알림은 Must(M11)에 포함. 묶음은 사슬에 필수는 아니다 | H9. 요청이 없는 주에도 돌아올 이유를 만든다 |
| S3a | 사용자 등록 외부 채널 알림 (Discord, KakaoTalk 등) | 이메일과 브라우저 알림으로 사슬은 돌아간다. 채널별 발송 가능성 확인 필요(OQ-4a) | 캠퍼스 구성원이 실제로 상주하는 채널이면 이메일보다 즉시성과 도달률이 높다 |
| S4 | 관심사 제안 (F16 일부) | 초기 100개로 시작 가능 | 원하는 관심사가 없어 이탈하는 사용자를 잡고, 목록 개선 신호를 얻는다 |
| S5 | 신고 (F15) | 거절·재요청 불가·횟수 상한으로 1차 방어는 된다 | 차단이 없으므로 신고가 운영자 개입의 유일한 경로. 조직 규모에서는 초기에 필요할 가능성이 높다 |
| S6 | 보낸 요청 취소 (FR-9.5) | 없어도 만료로 정리된다 | 실수로 보낸 요청을 되돌릴 수 없으면 요청 자체를 망설이게 된다 |
| S7 | Similar People 결과 없음 / 관심사 부족 시 안내 강화 (NFR-7) | 기본 빈 상태 문구는 Must에 포함 | 관심사를 더 고르도록 유도해 H1을 보강한다 |

### 3.3 Later

| # | 기능 | 왜 지금 넣지 않는가 |
|---|---|---|
| L1 | 댓글, 좋아요, 반응 | 커뮤니티로 변질되는 첫 단계. 게시글이 사람 발견에 기여하는지(H8) 확인 전에는 넣지 않는다 |
| L2 | 전체 피드 / 최신 글 타임라인 | 관심사와 분리된 글 소비는 Discovery 목적과 무관하다 |
| L3 | 사람 이름 검색 | Non-Goal. 아는 사람을 찾는 용도로 쓰인다 |
| L4 | 연결 해제 | MVP 기간 내 성립 연결이 많지 않다. 필요성은 데이터로 판단 |
| L5 | 첫 메시지 문안 자동 생성, 아이스브레이커 질문 | 시작자 지정과 소재 제공(M10a)까지는 Must. 문안까지 써주는 것은 성립 사례를 본 뒤 판단 |
| L6 | 운영자 대시보드, 관심사 관리 UI | 초기에는 운영자가 목록을 직접 준비하는 것으로 충분 |
| L7 | 모바일 그래프 탐색 | Non-Goal. 모바일은 요청 처리만 |
| L8 | 관심사별 사람 수 순위, 트렌드 | 흥미 요소이지만 연결 행동에 기여하지 않는다 |
| L9 | 추천 새로고침 주기 설정, 추천 숨기기 | 추천 피로가 관찰된 뒤 대응 |
| L10 | 프로필 한 줄 소개, 직무 등 확장 필드 | OQ-3 결정 후. 초기에는 관심사가 프로필의 전부여야 관심사 등록 동기가 유지된다 |

## 4. Should Have 두 항목에 대한 판단 근거

### 4.1 Interest Post (S1)

Phase 0에서 "아주 자연스럽다"고 확인된 기능이지만 Must로 올리지 않는다.

- 게시글 없이도 Interest Focus는 사람 목록을 보여주므로 Discovery Loop는 끊기지 않는다.
- 초기 8주 동안 1,000명 중 글을 쓰는 사람은 소수일 가능성이 높다. 글이 없는 관심사가 대부분이면 게시글 영역은 빈 화면이 된다.
- 반대로 글이 활발하면 댓글 요구가 생기고 커뮤니티로 흐른다.

**MVP에 넣는 조건**: 댓글, 좋아요, 피드가 없는 최소 형태. 글의 유일한 출구는 "작성자 프로필 보기"다. 이 형태로도 글에서 프로필로 이동하는 비율이 낮으면 Later로 내린다.

### 4.2 Network Recommendation (S2)

Phase 0에서 개념이 승인되었고 서비스의 차별점이지만 Must로 올리지 않는다.

- 성립 조건이 까다롭다. 전원 공통 관심사 5개 이상인 3~6명 그룹이 실제로 얼마나 존재할지는 관심사 분포를 보기 전에는 알 수 없다. 후보가 0개면 기능은 빈 화면이다.
- 후보가 있어도 3명 이상이 각자 참여를 눌러야 한다. 1:1 수락률이 50%라면 3명 동시 참여 확률은 훨씬 낮다.
- Phase 0에서 이미 그래프 표현의 가독성 문제가 관찰되었다.

**MVP에 넣는 조건 (데이터 게이트)**: 온보딩 후 실제 관심사 데이터로 후보 그룹 수를 먼저 확인한다. 사용자 1인당 평균 1개 이상의 후보가 있을 때만 노출한다. 그 전까지는 기능을 숨긴 채 후보 수만 운영자가 본다. 이 게이트는 OQ-8의 답이다.

## 6. MVP 종료 기준

MVP 기간(8주 가정)이 끝났을 때 아래 셋을 판단한다. 목표치는 02_PRD 9절의 가설이다.

| 판단 | 조건 | 다음 행동 |
|---|---|---|

## 7. 결정 사항 / 미결정 사항 (Step 2)

### 결정됨

- Must Have는 "관심사 등록 → 발견 → 이해 → 요청 → 수락 → 메신저 이동" 사슬로만 구성한다. 차단 기능은 제공하지 않는다(사용자 결정).
- 기본 그래프는 사용자 중심 부분 그래프다. 전체 그래프는 제공하지 않는다.
- 연결 요청 메시지는 필수다.
- 거절은 상대에게 직접 통보하지 않는다.
- 간편 로그인(기존 계정 사용) + 초대 링크 가입. 소속은 검증하지 않고 사용자를 신뢰한다. 다중 조직 확장 시 권한자 발급 초대장 구조로 간다(Later).
- 표시명은 닉네임과 실명 중 사용자가 선택한다. 실명 사용자는 표시가 붙는다. 연결 성립 시에는 누구나 실명이 공개된다.
- 소속 정보는 표시하지 않는다(단일 캠퍼스).
- 연결 성립 시 시작자를 지정하고 구체적 행동을 안내한다. 1:1은 요청 보낸 사람, Network는 가장 먼저 연결하기 버튼을 누른 사람.
- 알림은 이메일 즉시 알림 + 브라우저 알림(허용 시)이 Must Have. 사내 메신저 알림은 불가. 묶음 알림과 사용자 등록 외부 채널(Discord 등)은 Should Have.
- 게시글은 댓글, 좋아요, 피드 없는 최소 형태로 Should Have.
- Network 추천은 Should Have이며 실제 데이터로 후보 수를 확인한 뒤에만 노출한다.
- 연결 후 "대화를 시작하셨나요?" 후속 확인은 Must Have다.
- 성공 지표에서 가입자 수, 페이지뷰, 세션 길이는 제외한다.
