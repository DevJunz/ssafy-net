● 문서와 코드를 훑어서 현재 진행 상황을 정리하겠습니다. CLAUDE.md, 최근 커밋, history/, design/23 순으로 읽습니다.

**결론.** MVP 기능은 전부 구현되어 있고, 2026-09-09까지의 작업이 모두 커밋·푸시되어 로컬 main이 원격과 같습니다. 다음 순서는 CLAUDE.md에 **배포 → 모니터링 논의**로 확정되어 있습니다.

**완료된 것**

| 범위 | 상태 |
|---|---|
| M1~M5 (기반·발견·연결·알림·Should) | 완료. 로그인·온보딩이 실제 Google 계정으로 끝까지 돈다 |

**남은 것.** 코드로 확인한 미구현 항목입니다. design/23이 닫을 순서를 정해 두었습니다.

- **배포**가 첫 번째입니다. 저장소에 Dockerfile, Caddyfile, 운영용 compose가 하나도 없습니다. 지금 compose는 개발용 Postgres만 띄웁니다.
- 배포에 같이 넣기로 한 두 가지도 아직 없습니다. `/api/health` 엔드포인트와 종료 훅이 없고, Mattermost `fetch`에 타임아웃이 없습니다.
- **알림 발송 동시성·재시도.** `notify()`가 여전히 응답을 기다리지 않고 던지고, 실패는 시도 횟수만 올립니다.
- **운영자 레버.** 운영자 엔드포인트는 잡 실행·이력 둘뿐입니다. 정지, 관심사 병합·숨김, 기능 플래그 켜기가 없어 지금은 SQL 직접 실행입니다.
- **전역 rate limit과 쓰기 멱등성.** throttler 없음. 수락 더블클릭이 500을 냅니다.
- **측정(analytics)** 은 통째로 미구현입니다. 공개 전에 넣을지 정해야 합니다.
- 작은 것: 요청 로거가 OAuth 콜백의 `code=`를 그대로 남깁니다. 운영에서 쿼리스트링을 지워야 합니다.

**이 컴퓨터의 환경 상태**

- `api/.env`는 있고 필요한 키가 전부 채워져 있습니다.
- **Docker Desktop이 꺼져 있습니다.** DB를 띄우려면 먼저 실행해야 합니다.
- `dist` 폴더들이 있어 shared 빌드는 되어 있습니다.

**바로 시작할 수 있는 것.** 배포를 하려면 먼저 어디에 올릴지가 필요합니다. design/23은 AWS 서울 EC2 t4g.small 또는 Lightsail 4GB를 권하고, 이미 확보한 VM이 있으면 그것을 씁니다. 대상이 정해지면 Dockerfile·Caddyfile·운영 compose·헬스체크·웹훅 타임아웃을 한 묶음으로 만들 수 있습니다. 서버가 아직 없어도 그 묶음은 로컬에서 만들고 검증할 수 있으므로, 원하시면 그것부터 진행하겠습니다.

❯ 일단 확인용으로 서버 켜줘 그리고 배포는 오라클 클라우드로 할거야 여기 클라우딩 파워가 강력한데 무료로 지원되거든

● 서버를 켜겠습니다. Docker Desktop이 꺼져 있으니 그것부터 띄우고, DB → API → 웹 순으로 올립니다. 배포 대상이 오라클 클라우드로 정해진 것은 기록해 두겠습니다.

● DB가 살아 있고 사용자 126명이 들어 있습니다. API와 웹을 백그라운드로 띄웁니다.

● 남은 nest 프로세스를 정리했습니다. 이제 API를 다시 띄우고 응답을 확인합니다.

● 서버가 전부 떠 있습니다.

| 구성 | 주소 | 상태 |
|---|---|---|
| Postgres | Docker `ssafy-net-db` | 실행 중, 사용자 126명 |
| API | http://localhost:3000/api | 응답함 |
| Swagger | http://localhost:3000/api/docs | 응답함 |
| 웹 | http://localhost:5173 | 응답함, `/api` 프록시 정상 |

**한 가지 걸린 것.** 지난 세션에서 Swagger를 추가하며 `@nestjs/swagger` 의존성이 생겼는데 이 컴퓨터에는 설치되어 있지 않아 API가 컴파일에 실패했습니다. `npm install`을 돌려 해결했습니다. 다른 컴퓨터에서 커밋을 당겨온 뒤에는 이걸 먼저 돌려야 합니다.

**오라클 클라우드 결정은 기록했습니다.** CLAUDE.md의 다음 세션 항목과 제 메모리에 남겼습니다. 커밋은 하지 않았습니다.

오라클 무료 티어로 갈 때 미리 알아둘 것이 둘 있습니다.

- **ARM입니다.** Always Free의 큰 인스턴스는 Ampere A1이라 Docker 이미지를 linux/arm64로 만들어야 합니다. Node와 Postgres 공식 이미지는 모두 arm64를 지원하므로 문제는 없고, 빌드만 VM 위에서 하거나 multi-arch로 하면 됩니다.
- **인스턴스 확보와 회수.** 서울 리전은 A1 용량 부족으로 생성이 자주 거부됩니다. 그리고 7일간 CPU·네트워크 사용이 낮으면 유휴로 판정해 회수할 수 있는데, 공개 전 대기 기간에 걸릴 수 있습니다. 이미 인스턴스를 확보하셨는지가 첫 질문입니다.

배포 묶음(Dockerfile, Caddyfile, 운영 compose, 헬스체크, 웹훅 타임아웃)은 인스턴스가 없어도 지금 로컬에서 만들고 검증할 수 있습니다. 브라우저에서 확인해 보시고, 이어서 그 묶음을 시작할지 말씀해 주세요.

❯ 홈영역을 어디로 설정해야할까?

● 홈 영역은 가입 후 바꿀 수 없고 Always Free 인스턴스는 홈 영역에서만 만들 수 있어서 중요한 선택입니다. 최근 A1 용량 상황을 확인하고 답하겠습니다.

● **춘천(South Korea North, `ap-chuncheon-1`)을 권합니다.** 서울 캠퍼스 기준 지연 차이는 몇 ms라 이 앱에서는 구분이 안 되고, 무료 계정이 A1(ARM)을 잡을 확률은 사람들이 기본으로 고르는 서울보다 춘천이 낫습니다.

판단에 쓴 사실입니다.

- **홈 영역은 가입 후 못 바꾸고, Always Free 컴퓨트는 홈 영역에서만 만들 수 있습니다.** 그러니 "일단 서울로 하고 안 되면 다른 데서"가 불가능합니다. 처음에 정한 곳이 서버 위치입니다.
- **무료 A1 한도가 올해 6월 15일에 절반으로 줄었습니다.** 지금은 2 OCPU · 12GB입니다. 우리 권장 사양이 2 vCPU · 4GB라 여전히 충분합니다. x86 무료 인스턴스는 1GB라 부족합니다.
- **국내 두 리전 모두 무료 계정으로는 A1이 "Out of host capacity"로 자주 막힙니다.** 2025년 10월 가이드도 국내 리전에서 A1 생성이 어렵다고 적고 있고, 서울이 가장 붐빕니다. 춘천이 더 잘 잡힌다는 것은 사용자 경험담이라 보장은 아닙니다.
- **기획 문서에 데이터 국내 보관 규칙은 없습니다.** 그래도 실명이 들어가는 서비스라 국내 리전이 설명하기 쉽습니다. 도쿄·오사카는 A1이 잘 잡히지만 국외라 마지막 대안으로만 둡니다.

가입 뒤에 이렇게 되는지 봐야 합니다.

1. 춘천에서 `VM.Standard.A1.Flex` 2 OCPU · 12GB 생성을 시도합니다. 한 번에 되면 끝입니다.
2. 용량 오류가 나면 두 길이 있습니다. 자리가 날 때까지 자동 재시도하거나, **Pay As You Go로 전환**합니다. 카드를 등록해도 무료 한도 안에서는 청구가 없고, 전환 계정은 용량 제한을 대체로 통과합니다.
3. **유휴 회수 규칙**을 알아둬야 합니다. 7일 동안 CPU p95, 네트워크, 메모리 사용률이 모두 20% 아래면 무료 인스턴스를 회수할 수 있습니다. 공개 전 대기 기간에 걸릴 수 있는데, PAYG 전환 계정은 이 규칙에서 빠집니다. 그래서 PAYG 전환은 2번 문제와 이 문제를 한 번에 풉니다.

❯ 니가 웹 브라우저 열어서 봐바 춘처이 안나오네

● 브라우저를 열어 오라클 가입 화면의 홈 영역 목록을 직접 보겠습니다.

● 춘천 리전은 공식 문서에 아직 있습니다. 이제 "Always Free 지원 리전" 표에서 춘천이 빠져 있는지 봅니다.

● 확인됐습니다. 탭을 닫고 알아낸 것을 메모리에 남긴 뒤 정리하겠습니다.

● 춘천이 없는 건 리전이 사라진 게 아니라 **가입 화면의 홈 영역 목록이 그때그때 바뀌기** 때문입니다.

확인한 사실입니다.

- 오라클 공식 리전 문서에는 South Korea North(Chuncheon)가 지금도 있습니다. 리전 자체는 살아 있습니다.
- 올해 5월 10일에 가입한 한국 블로거는 정반대로 **서울이 목록에 없어서 춘천을 골랐다**고 적었습니다. 2020년 가이드에는 둘 다 있었습니다.
- 즉 오라클은 무료 계정 홈 영역 목록에서 **그 순간 무료 티어 여유가 없는 리전을 빼 버립니다.** 오늘은 춘천이 빠진 차례입니다.

제가 직접 볼 수 없었던 이유도 말씀드립니다. 홈 영역 선택은 이메일 인증 뒤 단계라 가입을 진행해야 보이는데, 계정 생성은 제가 대신할 수 없는 작업입니다. 그리고 지금 보고 계신 탭은 제 브라우저 그룹 밖이라 제 눈에 안 들어옵니다.

**결정 규칙은 이렇게 하시면 됩니다.**

1. **서울(South Korea Central)이 있으면 서울을 고르세요.** 서울 캠퍼스 기준으로 춘천과 지연 차이는 의미가 없고, 오늘 목록에 서울이 남아 있다는 것 자체가 지금은 서울 쪽에 여유가 있다는 신호입니다. 춘천이 다시 나타나길 기다릴 이유가 없습니다.
2. **한국 리전이 둘 다 없으면 오사카나 도쿄**를 고르세요. 서울에서 30~40ms라 이 앱에서는 체감이 없습니다.
3. 가입 뒤 A1(2 OCPU · 12GB) 생성에서 "Out of host capacity"가 나면, 앞서 말한 대로 재시도하거나 Pay As You Go로 전환합니다. 전환하면 유휴 회수도 피합니다.

❯ 근데 지금 화면에서 추천하는 네트워킹이 안보이네?

● Network 추천이 안 보이는 건 기능 플래그 때문일 가능성이 큽니다. DB에서 플래그 상태와 후보 계산 여부를 확인하겠습니다.

● 안 보이는 게 맞습니다. 이유는 둘이고, 둘 다 설계대로 동작한 결과입니다.

| 확인한 것 | 값 | 의미 |
|---|---|---|
| `network_enabled` 플래그 | 꺼짐 (9월 8일 설정) | 꺼져 있으면 아무것도 노출하지 않는다(D-75). 게이트 판정 뒤 운영자가 켜는 구조 |
| 후보(network_candidate) | 0개 | 후보 재계산이 하루 2회 인프로세스 cron인데, 서버가 꺼져 있던 동안 돌지 않았다. 마지막 실행은 9월 8일 15시 |
| 발송 모드 | redirect | 켜도 DM은 운영자 채널로만 간다. 안전하다 |

그러니 플래그를 켜는 것만으로는 안 나옵니다. 후보를 먼저 만들어야 하고, 그 다음 노출이 붙습니다.

로컬에서 확인하려면 이 순서입니다.

1. 로그인한 브라우저에서 Swagger(`localhost:3000/api/docs`)를 엽니다. 운영자 엔드포인트는 세션 쿠키가 필요해서 curl로는 401이 납니다. 같은 `localhost`라 포트가 달라도 쿠키가 따라갑니다.
2. `POST /api/admin/networks/recompute`를 실행합니다. 후보 수가 응답으로 옵니다. 더미 126명이라 1인당 1개 이상이 나오면 게이트 기준(docs/10 §4)을 통과한 셈입니다.
3. 플래그를 켭니다. 켜는 엔드포인트가 아직 없어서 SQL로 직접 합니다.

```bash
docker exec -i ssafy-net-db psql -U ssafynet -d ssafynet \
  -c "update feature_flag set enabled = true where key = 'network_enabled';"
```

4. 30초 기다린 뒤(파라미터 캐시) `POST /api/admin/networks/expose`를 실행합니다. 그때 추천이 화면에 나타나고 알림이 운영자 채널로 갑니다.

플래그를 켜는 엔드포인트가 없는 것은 docs/16 D-75에 "남은 것"으로 적혀 있고, CLAUDE.md의 운영자 레버 항목에 포함되어 있습니다. 원하시면 제가 위 절차를 대신 돌려 화면에 나오게 해 두겠습니다.

❯ 켜봐

● 켜겠습니다. 먼저 운영자 엔드포인트가 curl로 열리는지 확인하고, 안 되면 로그인된 브라우저 세션으로 실행합니다.

❯ 근데 컴퓨팅 인스턴스를 ecs로 해도되지 않을까? 크레딧이 여유있는데?

● GCP에는 ECS가 없습니다. ECS는 AWS 용어이고, GCP에서 같은 자리에 있는 것은 **Cloud Run**(서버리스 컨테이너)과 **GKE**(쿠버네티스)입니다. 어느 쪽을 뜻하셨든 결론은 같습니다. **이 코드베이스에는 VM 한 대가 맞고, 크레딧 여유는 VM을 한 단계 키우는 데 쓰는 편이 낫습니다.**

컨테이너 서비스를 권하지 않는 이유는 비용이 아니라 구조입니다.

- **배치가 인프로세스 cron입니다.** API 프로세스는 정확히 하나여야 하고, 둘이면 같은 알림이 두 번 나갑니다(design/20 §7). Cloud Run은 인스턴스 수를 0에서 N으로 늘렸다 줄이는 게 본업이라, 최소·최대를 1로 못 박고 CPU 상시 할당까지 켜야 겨우 VM 흉내가 납니다. 그러면 Cloud Run을 쓰는 이유가 없어집니다.
- **Postgres가 어딘가에 있어야 합니다.** Cloud Run은 DB를 못 품으니 Cloud SQL이 따로 붙습니다. 가장 작은 인스턴스도 월 $10~30이고, 연결 설정과 백업 정책이 하나 더 생깁니다. VM에서는 같은 compose 안의 컨테이너 하나입니다.
- **같은 출처를 전제합니다.** 세션 쿠키가 `sameSite: lax`이고 프론트는 `/api` 상대 경로라, 프론트와 API가 한 도메인 뒤에 있어야 합니다(design/23 §3). Cloud Run은 서비스마다 주소가 달라 로드밸런서를 앞에 세워야 하고, 그러면 Caddy 한 줄로 끝나던 TLS와 라우팅이 설정 여러 장이 됩니다.
- **로드밸런싱과 확장이 필요 없습니다.** 실측 처리량이 현실 최대 부하의 20배입니다(design/23 §4). 2주 동안 1,000명이 쓰는 서비스에 오케스트레이션은 얻는 것 없이 배울 것만 늘립니다.

**크레딧을 쓰고 싶다면 VM 사양을 올리세요.** 지금 문서의 e2-medium은 공유 코어라 CPU를 다른 VM과 나눠 씁니다. 크레딧 안에서 전용 코어로 바꿀 수 있습니다.

| 머신 | 사양 | 서울 월 요금(대략) | 90일 |
|---|---|---|---|
| e2-medium | 2 vCPU 공유 · 4GB | 약 $30 | 약 $90 |
| **e2-standard-2** | 2 vCPU 전용 · 8GB | 약 $60 | 약 $180 |
| e2-standard-4 | 4 vCPU 전용 · 16GB | 약 $115 | 약 $345, 크레딧 초과 |

**e2-standard-2를 권합니다.** 공개 첫날 몰리는 순간에 공유 코어의 CPU 제한을 걱정하지 않아도 되고, 부하 실측이 전용 코어 기준이라 그 숫자가 그대로 적용됩니다. 90일을 다 써도 $300 안입니다. e2-standard-4는 서버를 두 달 안에 지운다는 전제에서만 맞고, 그럴 이유가 없습니다.

배포 묶음은 머신 크기와 무관합니다. `deploy/README.md`의 VM 표에서 머신 이름 한 줄만 바뀝니다. 정하시면 그 줄을 고치겠습니다.

❯ gemini로 머신 유형 추천 생성하기 프롬프트에 뭐라고 입력할까

● 그 입력창에는 워크로드를 서술하면 됩니다. 아래를 그대로 붙여 넣으세요.

```
Docker Compose로 컨테이너 3개를 24시간 돌리는 웹 서비스용 VM 한 대입니다.
구성: Node.js 22 API 서버(NestJS) 1개, PostgreSQL 16 1개, Caddy 리버스 프록시 1개.
사용자 약 1,000명, 최대 초당 15요청 수준이고 평소에는 그보다 훨씬 낮은 간헐적 부하입니다.
DB 크기는 1GB 미만이고 메모리 사용은 전체 2GB 안쪽입니다.
요구 사항: x86-64, vCPU 2개, 메모리 4GB, 부팅 디스크 40GB, Ubuntu 24.04 LTS, 리전 asia-northeast3.
GPU 불필요. 확장 없이 인스턴스 1대로 장기 운영합니다.
우선순위는 월 비용 최소화이며 공유 코어(E2 계열)도 괜찮습니다.
가장 저렴한 머신 유형을 추천해 주세요.
```

예상 답은 **e2-medium**입니다. 다른 걸 내놓으면 이렇게 판단하세요.

- **e2-small**(2GB)을 주면 무시합니다. Postgres와 Node를 같이 올리기에 메모리가 빠듯합니다.
- **e2-standard-2**를 주면 "공유 코어도 괜찮다"는 조건을 못 읽은 겁니다. 월 $30 더 비쌉니다.
- **n1, n2, t2d** 계열을 주면 E2보다 비싸니 e2-medium으로 직접 고릅니다.

추천은 참고일 뿐이고, 머신 유형 드롭다운에서 **E2 → e2-medium**을 직접 고르는 편이 빠릅니다.

❯ 이제 병렬적인 작업을 진행할거야 하나는 지금 fe ui를 shadcn/ui을 설치해서 전면 교체하는 작업을 진행할거야
그리고 나머지 작업은 지금 chrome창에서 서버 배포를 나와 함께 도와줘

● 두 갈래로 나눕니다. shadcn/ui 교체는 별도 워크트리에서 에이전트가 진행하고, 저는 이 세션에서 Chrome으로 배포를 같이 봅니다. 먼저 커밋 안 된 배포 묶음 상태와 web/ 구조를 확인합니다.

● GCP 콘솔이 로드될 시간을 주고 화면을 봅니다. 로그인 여부, 프로젝트 유무, 무료 체험 활성 여부를 확인해야 다음 단계를 정할 수 있습니다.

● API 활성화가 진행 중입니다(버튼이 스피너로 바뀜). 조금 더 기다렸다가 VM 생성 화면으로 직접 이동해 확인합니다.

● 알림 패널은 열렸지만 오류 때문에 이미지가 빠졌습니다. 화면만 다시 봅니다.

● API가 켜졌습니다(알림에 성공 3건). 화면은 이미 VM 생성 폼으로 넘어가 로딩 중입니다. 알림 패널을 닫고 폼이 뜬 뒤 화면을 봅니다.

● 찾기 도구가 접근성 트리를 못 읽어 실패했습니다. 좌표로 조작하기 위해 화면을 보고, 동시에 상호작용 요소 목록도 받아 둡니다.

● 필드 참조를 얻었습니다. 이름을 `ssafy-net`으로 바꾸고 리전 드롭다운을 열어 서울을 고를 수 있는지 봅니다.

● 서울 항목이 하이라이트됐습니다. 선택한 뒤 왼쪽 요약에서 "e2-medium, asia-northeast3"가 되는지 확인하고, 이어서 OS 및 스토리지 탭으로 넘어갑니다.

● 부팅 디스크 대화상자가 열렸습니다. 운영체제 콤보박스에서 "Ubuntu"를 타이핑해 선택하고 결과를 확인합니다. 버전과 크기는 그 뒤에 이어서 합니다.

● "Ubuntu"를 고른 뒤 버전 콤보박스를 열어 "24.04"로 걸러 봅니다. 두 화면을 한 번에 받습니다.

● x86/64 Ubuntu 24.04 LTS(2026-09-06 빌드)를 고르고, 크기 40GB를 넣은 뒤 확인 화면을 받고, "선택"으로 대화상자를 닫아 OS 탭 요약까지 한 번에 봅니다.

● 네트워킹 탭 화면이 오류로 빠졌습니다. 화면과 상호작용 요소 목록을 함께 받아 방화벽 체크박스 위치를 잡습니다.

● 찾기 도구는 이 폼에서 계속 실패하므로 좌표로만 조작합니다. 펼쳐진 nic0 화면을 봅니다.

● nic0 편집 영역이 열렸습니다. 외부 IPv4 항목은 더 아래에 있으니 스크롤해서 봅니다.

● "고정 외부 IP 주소 예약" 옵션이 있습니다. 클릭하면 이름을 묻는 대화상자가 뜰 겁니다. 열고 화면을 봅니다.

● 고정 IP 이름을 `ssafy-net-ip`로 넣고 "예약"을 눌러 외부 IPv4 드롭다운에 반영되는지까지 한 번에 확인합니다. 예약된 IP는 나중에 해제할 수 있습니다.

● IP 예약이 "생성 중"입니다. 몇 초 기다렸다가 결과 화면을 봅니다.

● VM 설정이 다 찼습니다. "만들기"만 남았는데 이것은 과금이 시작되는 단계라 직접 누르시거나 "눌러"라고 해 주세요.

**지금 폼에 들어간 값**

| 항목 | 값 |
|---|---|
| 이름 | ssafy-net |
| 리전 | asia-northeast3 (서울), 영역 자동 |
| 머신 | e2-medium (2 vCPU, 4GB) |
| OS / 디스크 | Ubuntu 24.04 LTS x86-64, 균형 영구 디스크 40GB |
| 방화벽 | HTTP, HTTPS 허용 |
| 외부 IP | 고정 `35.216.40.235` (ssafy-net-ip, 이미 예약됨) |
| 네트워크 계층 | 표준 (월 200GB 송신 무료) |
| 스냅샷 | 기본 일정(매일 저녁, 디스크만) 유지 |
| 예상 비용 | 월 $36.58, 크레딧에서 차감 |

Compute Engine API는 제가 켰고, 고정 IP 예약도 끝났습니다. 나머지 탭(모니터링, 보안, 고급)은 기본값 그대로 두는 게 맞습니다.
