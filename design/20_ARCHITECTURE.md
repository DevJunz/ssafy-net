## 1. 규모 전제와 그 귀결

MVP의 모든 기술 판단은 아래 숫자에서 나온다.

| 항목 | 값 | 근거 |
|---|---|---|
| 대상 인원 | 약 1,000명 (단일 캠퍼스) | docs/01 §1 |
| 시드 | 같은 반 26명 | D-55 |
| 사용 집중 기간 | 공개 후 2주 | D-33, A-10 |
| MVP 기간 | 4주 (집중 2 + 관찰 2) | D-35 |
| 동시 접속 추정 | 최대 수십 명 | 1,000명 × 웹 서비스 × 업무 시간 |
| 예상 최대 행 수 | User 1,000 · UserInterest 7,000 · ConnectionRequest 수천 · Post 수백 · AnalyticsEvent 수십만 | 02 §9, 14 |

**귀결: 이 서비스에 분산 시스템이 필요한 부분은 하나도 없다.**

| 하지 않는 것 | 이유 |
|---|---|
| 메시지 큐, 워커 분리 | 알림 발송량이 하루 수백 건이다. 인프로세스 처리로 충분하다 |
| Redis 등 캐시 계층 | 가장 무거운 쿼리(Network 후보)도 배치이고, 나머지는 7,000행 집계다 |
| 읽기 복제본, 샤딩 | 데이터가 한 대의 작은 DB에 다 들어간다 |
| 그래프 DB (Neo4j 등) | 관계 깊이가 2단계로 고정이고(06 §1.1) 전체 그래프 순회가 없다. 관계형으로 충분하며 집계·정렬이 오히려 쉽다 |
| 마이크로서비스 | 운영자가 한 명이다(D-57, R-16) |

이 아키텍처의 1순위 원칙은 성능이 아니라 **운영자 한 명이 2주 동안 매일 들여다볼 수 있을 만큼 단순할 것**이다.

## 2. 기술 스택

| 영역 | 선택 | 이유 | 검토한 대안 |
|---|---|---|---|
| Frontend | React 19 + TypeScript + Vite | Phase 0에서 검증된 구성 그대로. 그래프 렌더링 코드를 이식할 수 있다 | Next.js — SSR이 필요 없고 Phase 0 자산을 버리게 된다 |
| 그래프 렌더 | react-force-graph-2d | Phase 0에서 사용자 승인(D-00) | d3-force 직접 — 이득 없음 |
| Backend | NestJS (TypeScript) | 사용자가 Phase 0 프롬프트에서 지정. 프론트와 언어·타입 공유. 모듈·DI·스케줄러·검증이 기본 제공 | Express — 구조를 직접 만들어야 함 |
| DB | PostgreSQL 16 | 교집합·집계·부분 인덱스·배열·jsonb가 모두 필요하다(§6, 21) | MySQL — 배열/부분 인덱스가 없어 우회 필요 |
| ORM | Prisma | 스키마 파일 하나가 곧 ERD. 마이그레이션과 타입 생성이 자동 | TypeORM — 스키마가 여러 파일에 흩어져 ERD 대조가 어렵다 |
| 인증 | Google OAuth 2.0 + httpOnly 쿠키 JWT | 로그인은 Google만(D-56). 세션 테이블 없이 1,000명 규모에 충분 | 세션 테이블 — 이득 없음 |
| 스케줄러 | @nestjs/schedule (인프로세스 cron) | 배치가 하루 10회 남짓이고 단일 인스턴스다(§7) | 별도 워커 — 과하다 |
| 알림 | Mattermost 들어오는 웹훅 | 구성원이 상주하는 사내 메신저. 도달률이 가장 높다(D-66, D-67) | 이메일·Web Push — 만들지 않는다 |
| 로컬 DB | Docker Compose (postgres:16) | 이 PC에 Docker 29 있음, psql 없음 | 로컬 설치 — 재현성 낮음 |
| 검증 | Zod 스키마를 `packages/shared`에서 공유 | 요청 본문 검증과 프론트 폼 검증에 같은 규칙을 쓴다 | 각자 구현 — 규칙이 갈라진다 |

**Java/Spring을 쓰지 않는 이유**: 이 PC에 JDK 1.8만 있어 Spring Boot 3(JDK 17+)를 쓰려면 설치부터 필요하고, 프론트와 언어가 갈라져 1인 개발에서 문맥 전환 비용이 커진다. 사용자가 Phase 0 프롬프트에서 NestJS/PostgreSQL을 명시한 것과도 어긋난다.

## 5. 인증, 초대, 딥링크

### 5.1 가입 흐름 (FR-0.2, J0)

```
초대 링크 /invite/:code
   └─► code 유효성 확인 → 서명된 초대 쿠키(10분) 발급 → 소개 화면
        └─► "Google로 시작" → /auth/google?redirect=...
             └─► Google 동의 → /auth/google/callback
                  ├─ 기존 사용자: 세션 쿠키 발급 → redirect 또는 온보딩 재개 지점
                  └─ 신규 사용자: 초대 쿠키 필수. 없으면 "초대 링크가 필요합니다"
                       └─► User 생성(온보딩 미완료) → 실명·표시명 단계
```

- 초대 링크는 MVP에서 **하나**로 충분하다(FR-0.2). 다만 테이블로 두어 유출 시 폐기하고 새로 발급할 수 있게 한다(A-15).
- 소속 검증은 하지 않는다(D-20). 초대 코드 보유가 유일한 경계다.
- 온보딩 미완료자는 그래프·추천·다른 사용자 조회에 접근할 수 없고, 다른 사람에게도 보이지 않는다(FR-1.6). 이것을 가드 하나(`OnboardedGuard`)로 강제한다.

### 5.2 세션

| 항목 | 결정 | 이유 |
|---|---|---|
| 형태 | JWT를 httpOnly·SameSite=Lax·Secure(운영) 쿠키에 담음 | XSS로 토큰이 새지 않는다. 이메일 링크 클릭(다른 탭)에서도 전달된다 |
| 수명 | 30일, 갱신 없음 | 사용 기간이 2주다. 만료 재로그인 비용이 낮다 |
| 무효화 | 매 요청 시 사용자 조회 | 탈퇴·정지가 즉시 반영되어야 한다(09 §9, 12 §10) |
| 저장 테이블 | 없음 | 1,000명 규모에서 이득이 없다 |

### 5.3 알림 딥링크 (J6, 07 §6)

- 모든 알림 링크는 `/n/:deliveryId` 하나의 형태다. 서버가 (1) 클릭을 기록하고(14 §2.4 채널별 클릭률), (2) 로그인 여부를 확인하고, (3) 최종 목적지로 리다이렉트한다.
- 로그인이 풀려 있으면 `?redirect=`에 목적지를 담아 OAuth를 거친 뒤 **원래 목적지로 복귀**한다(06 §4 "로그인 세션 만료").
- 대상이 이미 처리되었으면 목적지 대신 "이미 처리된 항목입니다" 화면으로 보낸다(07 §6).

## 6. 그래프와 추천을 어디서 계산하는가

**원칙: 전부 PostgreSQL 쿼리로, 요청 시점에 계산한다. 단 하나의 예외가 Network 후보 생성이다.**

### 6.1 나 중심 부분 그래프 (06 §1.1)

| 계층 | 내용 | 상한 |
|---|---|---|
| 0 | 나 | 1 |
| 1 | 내 관심사 전부 | `[P-02]` 15 |
| 2 | 내 관심사를 가진 사람 중 공통 많은 순 | `[P-13]` 30 |
| 3 | 표시된 사람들이 가진, 내가 없는 관심사 중 보유자 많은 순 | `[P-14]` 8 |

계층 2의 **"내 관심사마다 최소 2명" 보정**은 순수 SQL로 표현하기 어렵고 설명도 어려워진다. 절차를 명시한다.

1. 내 관심사를 하나라도 가진 사용자를 공통 개수와 함께 모두 가져온다(온보딩 완료, 미탈퇴, 나 제외). 1,000명 기준 최대 수백 행이다.
2. `공통 개수 desc → 희소성 가중 desc → 가입 최신순`으로 정렬해 상위 `[P-13]`명을 뽑는다.
3. 내 관심사 중, 선택된 사람 안에서 보유자가 2명 미만인 관심사를 찾아 그 관심사 보유자 중 미선택자를 순위 순으로 채운다.
4. 인원이 `[P-13]`을 넘으면 **이미 다른 관심사가 2명 이상 확보된** 사람 중 순위가 가장 낮은 쪽부터 뺀다. 보정이 상한보다 우선한다.
5. 잘려나간 인원 수를 응답에 담는다("N명 더 있음", 06 §2).

정렬 기준은 화면에 그대로 표시된다(13 원칙 4). 따라서 이 절차는 사용자에게 설명 가능한 형태여야 하며 점수를 노출하지 않는다.

### 6.2 Similar People (13 §3)

```
공통 관심사 개수 >= [P-03] 3
정렬: 공통 개수 desc → 희소성 가중 합 desc → 가입 최신 desc
그래프 선: 상위 [P-15] 10명. 나머지는 목록
```

- 한 번의 집계 쿼리로 끝난다. `user_interest`를 내 관심사로 필터해 `GROUP BY user_id HAVING count(*) >= P-03`.
- **희소성 가중**(I-11, 13 §3.2): `w(i) = ln(1 + 온보딩완료자수 / max(1, 보유자수))`
  - 성질만 지키면 되는 자리다(13 §3.2 "가진 사람이 적을수록 큼"). 로그를 쓰는 이유는 1명만 가진 관심사가 정렬을 완전히 지배하지 않게 하기 위해서다.
  - **정렬에만 쓴다.** 값은 어떤 응답에도 넣지 않는다(13 원칙 2, D-51).
- 제외·구분 규칙은 13 §3.4를 그대로 따른다. **처리한 사람을 목록에서 지우지 않는다.** 사라지는 순간 설명 불가능한 추천이 된다.

### 6.3 Network 후보 생성 (10 §2) — 유일한 배치

"멤버 전원의 교집합이 `[P-04]` 5개 이상인 3~6명 그룹"은 조합 탐색이다. 1,000명에서 3~6명 부분집합을 전수 탐색할 수는 없다(C(1000,3)만 1.6억). 네 단계로 줄인다.

**1단계 — 쌍 사전 필터 (SQL).** 공통 관심사가 `[P-04]` 이상인 사용자 쌍만 남긴다.

```sql
SELECT a.user_id AS u1, b.user_id AS u2, count(*) AS c
FROM user_interest a
JOIN user_interest b ON a.interest_id = b.interest_id AND a.user_id < b.user_id
GROUP BY 1, 2
HAVING count(*) >= :p04
```

전원 교집합이 K 이상이면 그 안의 **모든 쌍**도 K 이상이다. 즉 필요조건이므로 여기서 걸러도 답을 잃지 않는다. 7,000행 self-join이라 인기 관심사가 있어도 수백 ms 안에 끝난다.

**2단계 — 탐욕적 확장.** 각 쌍에서 시작해, 모든 멤버와 이웃이면서 교집합을 가장 적게 깎는 사람을 하나씩 붙인다. 교집합이 `[P-04]` 미만이 되거나 `[P-05b]`명에 닿으면 멈춘다.

> **설계안(Bron–Kerbosch)에서 바꾼 지점.** 처음에는 크기 3~6의 클리크를 Bron–Kerbosch로 열거할 계획이었다. 실제 데이터로 돌려 보니 그럴 수 없었다. 개발자 조직에서는 인기 관심사 상위 4개를 절반 가까이가 갖고 있어(더미 120명 기준 백엔드 48% · 프론트엔드 46% · 취업 준비 48% · 알고리즘 43%) "공통 5개 이상인 쌍" 그래프가 희소하지 않다. 클리크 열거는 이런 조밀한 부분그래프에서 폭발한다.
>
> 탐욕적 확장은 **모든 극대 그룹을 찾지는 못한다.** 대신 시간이 선형에 가깝고 결과가 예측 가능하다. 후보 수가 부족하다는 신호가 나오면 그때 넓힌다 — 지금 필요한 것은 완전한 열거가 아니라 "설명 가능한 후보 몇 개"다.
>
> 차수 상한(이웃 60명)은 그대로 둔다. 상한에 걸리면 공통 개수가 큰 이웃부터 남긴다.

**3단계 — 교집합 검증.** 쌍 조건은 필요조건일 뿐 충분조건이 아니다. 확장 과정에서 교집합을 계속 유지하므로 결과는 정의상 `[P-04]` 이상이지만, 저장 전에 한 번 더 확인한다.

**4단계 — 극대성과 제외.**
- 다른 후보의 부분집합인 후보는 버린다(10 §2 "같은 사람들의 부분집합은 별도 후보로 만들지 않는다").
- 멤버 전원이 이미 서로 연결된 그룹은 제외(10 §2).
- 온보딩 미완료자, 요청 권한 정지자, 탈퇴자 제외.

정렬(10 §2a 우선순위): `전원 공통 개수 → 희소성 가중 → 신규 가입자(3일 이내) 포함 → 멤버 수 적은 순`.

**갱신 시점** (10 §2a):

| 트리거 | 범위 |
|---|---|
| 온보딩 완료 | 그 사용자를 포함하는 후보만 계산(1인 기준이라 가볍다) + 최선 1개 즉시 노출 |
| 관심사 변경 | 그 사용자가 포함된 **미노출** 후보만 재계산. 노출된 추천은 건드리지 않는다 |
| 탈퇴 | 후보와 노출된 추천에서 제거, 잔여 인원 3 미만이면 조기 소멸 |
| 성립 | 같은 멤버 집합 후보를 풀에서 제거 |
| 하루 2회 배치 (09:00, 18:00 KST) | 전체 재계산 + 빈 슬롯 노출 |

**후보 풀과 노출을 분리한다.** 풀은 언제든 바뀌고, 노출된 추천은 멤버·공통 관심사를 **스냅샷으로 고정**한다(10 §2a, D-45). 참여는 특정 사람들에 대한 의사 표시이므로 멤버가 바뀌면 안 된다.

### 6.4 캐시를 두지 않는 이유

- 관심사를 바꾸면 그래프와 추천이 **즉시** 달라져야 한다(NFR-5, 13 §3.5). 캐시는 이 요구와 정면으로 충돌한다.
- 가장 무거운 조회도 7,000행 집계다. 인덱스만 맞으면 수십 ms다.
- 캐시가 필요해지는 신호: 그래프 API p95가 300ms를 넘거나 1단계 쌍 필터가 3초를 넘을 때. 그때 도입할 것은 Redis가 아니라 **관심사별 보유자 수 비정규화 컬럼**이다(§12).

## 8. 알림 채널 추상화

> **2026-09-08 개정.** B-3/B-4는 확인할 필요가 없어졌다. Mattermost 들어오는 웹훅으로 개인에게 DM을 보낼 수 있음이 확인되어 **채널은 Mattermost + 앱 내 알림함 둘뿐**이다(D-66, D-67). 이메일·브라우저 알림·외부 채널은 만들지 않는다. 어댑터 구조는 그대로 두어 나중에 채널을 붙일 여지만 남긴다.

**어떤 채널이 죽어도 도메인 코드가 바뀌지 않는 구조**로 만든다. 이것이 알림 설계의 유일한 요구다.

```
도메인 사건 (요청 도착 · 수락 · 성립 · 재안내 · 후속 확인 · 묶음)
        │
        ▼
   NotificationService.create(userId, type, payload)
        │   ├─ Notification 행 생성 (앱 내 알림함은 항상 생성)
        │   └─ 사용자 설정 × 알림 카테고리로 발송 채널 결정
        ▼
   Dispatcher ──► InAppChannel      (항상. 유일한 대비책)
              └─► MattermostChannel (들어오는 웹훅)
        │
        ▼
   NotificationDelivery 행 (채널별 발송·실패·클릭 기록 → 14 §2.4)
```

| 규칙 | 내용 | 근거 |
|---|---|---|
| 앱 내 알림함은 항상 남는다 | 외부 채널이 전부 실패해도 로그인하면 보인다 | FR-14.1 |
| 즉시 / 묶음 구분 | 즉시: 받은 요청, 수락, 성립, 재안내, 후속 확인. 묶음: 새 Similar People, 새 글, Network 추천 | FR-14.2 |
| 알림 본문에 판단 근거 | 표시명, 공통 관심사 개수와 이름, 메시지 첫 줄 | FR-14.3 |
| 실명은 성립 알림에만 | 그 전에는 어떤 알림에도 넣지 않는다 | 12 §7 |
| Mattermost에는 실명을 넣어도 된다 | D-50이 실명을 금지한 이유는 "조직 밖 서비스"였다. 사내 메신저에는 그 이유가 성립하지 않는다 | D-66 |
| 알림에 행동 버튼 없음 | 수락은 판단 근거를 본 화면에서만 | D-25 |
| 받은 요청 알림은 최소 한 채널 강제 | 전부 끄려 하면 막는다 | FR-14.5 |
| 발송 직전 재확인 | 리마인드·재안내는 보내기 직전 상태를 다시 읽어 이미 처리됐으면 취소 | FR-14.6 |
| 실패는 지수 백오프로 3회 재시도 후 기록하고 포기 | 알림 실패가 요청 처리 트랜잭션을 막지 않는다 | — |

**발송은 도메인 트랜잭션 밖에서 한다.** 요청 생성 트랜잭션이 커밋된 뒤 알림을 만들고, SMTP 지연이 API 응답을 붙잡지 않도록 응답 후 비동기로 보낸다(인프로세스 큐 하나로 충분하다).

**Mattermost 웹훅의 제약** (실측, 2026-09-08)

| 제약 | 대응 |
|---|---|
| 발송만 되고 프로필 조회는 불가능 (토큰·봇 모두 막힘) | 아이디를 온보딩에서 직접 받고 코드로 확인한다(D-66) |
| 웹훅 생성자 본인에게는 DM이 가지 않는다 | 운영자 계정만 예외 경로 |
| 목적지를 빠뜨리면 기본 채널로 간다 | 기본 채널은 **운영자만 있는 비공개 채널**이어야 한다. 여기가 폭발 반경이다 |
| 채널이 하나뿐이라 웹훅이 막히면 외부 알림이 멈춘다 | 앱 내 알림함과 배지가 유일한 대비책이다. 어댑터 구조를 유지해 다른 채널을 붙일 여지를 남긴다 |

## 9. Product Parameter를 코드 상수로 두지 않는다

`[P-01]`~`[P-18]`은 **DB 테이블(`AppParameter`)에 둔다.** 이유는 명확하다.

- 공개 3일째에 P-03을 3→2로 낮추는 판단이 **이미 예정되어 있다**(13 §3.3, 14 §5).
- Network 게이트 미통과 시 P-04를 5→4로 낮추는 것도 예정되어 있다(10 §4).
- 그래프 상한 P-13~15는 "앱을 만든 뒤 피드백으로 조정"이 사용자 결정이다(D-34).
- 값을 바꾼 시점 전후로 지표를 나눠 봐야 한다(14 §1).

배포 없이 값을 바꾸고, 변경 이력을 남긴다. 프론트도 서버에서 파라미터를 받아 화면 문구("최소 5 · 최대 15")를 만든다. 상수를 코드에 박으면 화면과 서버가 갈라진다.

`FeatureFlag`는 별도로 둔다. 지금 필요한 것은 `network_enabled` 하나다(10 §4 — 게이트 통과 전에는 전역 내비에 "네트워크"가 없어야 한다).

## 10. 측정

- 프론트가 이벤트를 모아 `POST /events`로 보낸다. 서버 도메인 사건(요청 발송·수락·성립·만료)은 서버가 직접 기록한다. **서버가 아는 것은 프론트에 의존하지 않는다.**
- 이벤트 이름 목록은 14 §6을 그대로 옮긴다(22 §12).
- 대시보드는 만들지 않는다(L6). 운영자는 `api/scripts/`의 SQL을 실행한다. 14 §5의 판단 시점(1·3·7·14·28일)에 필요한 쿼리를 미리 파일로 준비한다.
- 이벤트에는 그 시점의 파라미터 값을 함께 남긴다(14 §1).

## 11. 공개 범위를 코드가 아니라 구조로 지킨다

12 §1의 공개 범위 표는 **응답 직렬화 계층에서 강제**한다. 컨트롤러마다 `if`로 처리하면 한 군데를 빠뜨리는 순간 실명이 샌다.

- 사용자 표현은 세 가지 뷰로만 만든다: `PublicUser`(표시명, 관심사, 글), `ConnectedUser`(+ 실명), `SelfUser`(+ 계정, 설정).
- 실명이 응답에 들어갈 수 있는 지점은 **셋뿐**이다: (1) 연결됨 상태의 상대, (2) 성립된 Network의 참여 멤버, (3) 나 자신.
- 연결 관계·연결 수·요청 이력·거절·신고는 제3자 응답에 어떤 형태로도 넣지 않는다(12 §5).
- 이 규칙의 회귀 테스트를 둔다. **"연결 전 사용자 조회 응답에 realName 키가 없다"** 는 테스트 하나가 이 서비스에서 가장 중요한 테스트다.

**단일 VM + Docker Compose**를 기본안으로 둔다. 확정은 구현 후반으로 미룬다. 1,000명·2주 규모에서 관리형 서비스를 조합하는 비용이 얻는 것보다 크고, 배포 대상이 하나면 배치 중복 실행 문제도 없다.

| 구성 | VM 1대에 `api` + `postgres` + 리버스 프록시(Caddy: TLS 자동) |

## 14. 구현 순서

기획의 사슬(H1→H5)이 끊기지 않는 순서로 간다. 각 단계 끝에서 **그 단계까지만으로 사용 가능**해야 한다.

| 마일스톤 | 범위 | 끝났을 때 가능한 것 |
|---|---|---|
| **M1 기반** ✅ | 저장소 구성, Prisma 스키마, 마이그레이션, 관심사 시드(B-1 초안), 인증·초대, 온보딩 | 초대 링크로 가입하고 관심사를 고를 수 있다 |
| **M2 발견** ✅ | 그래프 API + 화면, Interest/Person 패널, Similar People, Similarity Edge | H1·H2를 검증할 수 있다 |
| **M3 연결** ✅ | 요청·수락·거절·만료·취소, Connections 3탭, 성립 화면과 Action 안내, 후속 확인 | **사슬이 완성된다. 여기까지가 Must(M0~M14)** |
| **M4 알림** | 앱 내 알림함, 배지, **Mattermost 발송**, 배치 잡, 딥링크 | 앱을 열지 않아도 요청을 알 수 있다 |
| **M5 Should** ◐ | Network 후보·노출·참여·성립(S2) **완료**. 남은 것: Interest Post(S1), 신고(S5), 관심사 제안(S4), 묶음 알림(S3) | H6·H8을 검증할 수 있다 |

- **M3까지가 MVP의 최소선**이다. 일정이 밀리면 M5부터 뺀다(03 §2 분류 원칙).
- ERD와 API는 M5까지 **전부 설계**한다. 나중에 스키마를 뒤집는 비용이 지금 설계하는 비용보다 크다.
- 모바일은 M3·M4에서 Connections·Notifications·Overlay만 반응형으로 처리한다(06 §5). 그래프는 PC 전용이다.
